### 2.2 为什么需要它

插件侧的完整链路，**卡在这一个环节**：

```
买家发图
   ↓
良票识别          cityCode=350900  cinemaId=7261  showId=<良票的>
   ↓
映射（★ 已通）     → 万达 city=80  cinema=379
   ↓
★★ 这里缺一步：用万达 cinema=379 取【万达的 showtimeId】
   ↓
桥 /api/showtime/seats?showtimeId=…  → 会员价（成本）
   ↓
规则引擎（每张 +1 元）→ 报价
```

**为什么不能跳过这一步**：`/api/showtime/seats` 只吃**万达的**
`showtimeId`，而良票识别给的是**良票的** `showId` —— 两套 ID 体系，
`showId` 不在 `cinema_identity_mapping` 里（那张表只映射影院，不映射场次）。

**我实测过：拿良票的 showId 去调 `/seats`，返回**

```json
{"code":0,"data":{"bizCode":1000015,"bizMsg":"服务器繁忙,请稍后再试",
                  "realtimeSeats":null}}
```

★ 这个错误信息会误导人以为是限流/账号问题，其实是**场次 ID 不对**。
（我已经把它做成明确报错：`WANDA_BIZ_1000015`，并在消息里点明"不一定是限流"。）

### 2.3 请求

**把 `/api/showtime/by-cinema` 加进 `_INTERNAL_BRIDGE_KEY_API_PATHS`。**

就这一行。不需要新写代码 —— 路由已存在、已带缓存。

```python
_INTERNAL_BRIDGE_KEY_API_PATHS = {
    "/api/auth/internal/wplus-accounts",
    "/api/cinema/wanda-lookup",
    "/api/order/match",
    "/api/order/internal/wplus-price",
    "/api/order/internal/wplus-recovery",
    "/api/showtime/by-cinema",     # ★ 新增
    "/api/showtime/seats",
    "/api/integration/orders/events",
}
```

**为什么不是新增一个"场次匹配"接口**：
把「按影片名+开映时间匹配场次」放在插件侧更合适 ——
**那是报价逻辑的一部分**（要跟买家截图上的影片/时间对齐），
而且策略会随业务变（容差多少分钟、要不要按厅型筛）。
出票系统只提供原料（某影院某天的全部场次）就够了，职责更干净。
