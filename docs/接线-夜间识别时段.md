## 一、★ 发现的错：我的时间窗判定不支持【跨午夜】

做夜间识别时才注意到：**它的默认时段是 `23:30 ~ 08:00`** ——
**start 比 end 大，跨过了午夜。**

而我上一轮在退款时序里写的判定是：
```python
if t < (sh, sm, ss) or t > (eh, em, es):   # 等价于 start <= now <= end
    return False
```
**跨午夜时这个条件永远成立**（`now >= 23:30` 且 `now <= 08:00` 不可能同时为真）
⇒ **那种配置会变成"永远不许"**。

**实测对照**（这就是证据）：
```
夜间 23:30~08:00：
    23:29:59 → False ✓      23:30:00 → True ✓
    00:00:00 → True ✓       02:48:00 → True ✓
    08:00:00 → True ✓       08:00:01 → False ✓
朴素写法 `(23,30,0) <= (2,48,0) <= (8,0,0)`  ⇒  False（必然错）
```

**★ 修法不是"在夜间识别里再写一份对的"** —— 那会留下两份实现，
修了一处忘了另一处（**正是我在关键词话术那次刚消灭的老毛病**）。

**⇒ 抽出 `application/time_window.py`，两处共用：**
```python
def in_range(start_raw, end_raw, *, now=None) -> bool:
    """边界含头含尾；start > end ⇒ 跨午夜（或判）"""
```

**修完验证**：
```
退款时序原有（10:00~18:00）行为没变 ✓   27/27 项照过 ✓
夜间识别（23:30~08:00）跨午夜正确 ✓
坏输入（空/abc/99:99:99）⇒ 回退成全天，不是"永远关闭" ✓
```

## 二、接了夜间识别提醒

**语义（按字段定义直读）**：
```
start/end  提醒时段（默认 23:30~08:00）
message    label 写的是「**补充**提醒话术」
⇒ 所以是【追加一条提醒】，不是替换识别结果、也不是拦住识别。
```

**这件事很重要**：深夜买家**还是能下单的**，我们只是提醒他
"这个时间段可能出票失败"。

**放在哪**：`out.add("RECOGNIZING_TIP")` 之后、**识别之前**。
```
★ 为什么在识别之前：
  ① 这条和识别结果无关（不是"识别失败了"才说）
  ② 识别要 3.7~5 秒 —— 提醒早点发，买家不用等完才知道
```

**四条不猜的取舍**：

| 取舍 | 做法 | 理由 |
|---|---|---|
| 追加还是替换 | **追加到 messages** | label 写的是「补充」 |
| 位置 | 识别**之前** | 与结果无关；且识别要 5 秒 |
| 提醒失败 | **只记 note，不影响识别** | 识别才是买家要的，提醒是附赠 |
| 时段判定 | **共用 time_window** | 不重复实现（见上） |

## 四、★ 一个我自己制造的"测试假象"

测试里我写了：
```python
hhmm = f'{now.hour:02d}:{now.minute:02d}'      # 只有分钟精度
print(in_range(hhmm, hhmm, now=now))           # → False，看着像 bug
```
**但这不是 bug**：`hhmm` 解析成 `02:48:00`，而 `now` 是 `02:48:37`
⇒ 现在时刻落在 `start` 之后 37 秒，而 `end` 就是 `02:48:00`
⇒ 确实不在区间内（含头含尾，但 37 秒超出尾了）。

**⇒ 用固定时刻重测，结果全对。**
**★ 教训：拿"当前时间"当测试输入，会造出看起来像 bug 的假象。**
时间相关的判定，**输入必须是固定的时刻**。
