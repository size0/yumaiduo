## 〇、我接万达时犯的错（先说，因为这份设计就是改它）

我落单后直接发了 `TICKETING`（bubble 7）——**那是【付款后】才该发的**。
正确的顺序是：拍下 → 改价/核价 → **付款前发购票须知** → 付款 → 出票时间。

而且 `TICKETING` 的文案里有**取票链接**：

```
取票链接（可自行查看进度）：{pickup_link}
```

★ 那是良票【下单就返回】的免登录取票页。**万达是店家手动出票，没有这个链接。**

## 一、完整流程（两条渠道并列，标出差异）

| # | 时刻 | 状态 | 该发什么 | 良票 | 万达 |
|---|---|---|---|---|---|
| 1 | 买家发截图 | IDLE→RECOGNIZING | `RECOGNIZING_TIP` 🔒 | 同 | 同 |
| 2 | 识别成功 | →QUOTED | `QUOTE_CARD` | 同 | 同 |
| 3 | 买家确认/拍下 | →AWAIT_REPRICE | `ORDERED_NO_PAY` 🔒 | 同 | 同 |
| 4 | **价格锁定** | →AWAIT_PAY | `REPRICED_CHECK` 🔒 | ★ **我们改价后** | ★ **本来就是一口价，无需改价** |
| 5 | **付款前** | AWAIT_PAY | `PURCHASE_NOTICE` 🔒 | 同 | 同 |
| 6 | 付款事件到 | →AWAIT_TICKET | `TICKETING` | 有取票链接 | ★ **无链接** |
| 7 | 出票凭证 | →DELIVERED | `TICKET_CODE` | 有取票链接 | `TICKET_CODE_MANUAL`（★ 已有，就是为这个场景拆的） |
| 8 | 售后 | — | 退款四条 | 同 | 同 |

**★ 良票和万达的差异只有两处：**

```
① 第 4 步：良票要"改价"（价格先报后定），万达不用（成本确定，价一开始就定）
② 第 6/7 步：良票有取票链接，万达没有
```

### 2.1 ✅ 已做：`TICKETING` 加万达渠道覆盖 —— 去掉取票链接


### 2.3 ✅ 已做：付款事件的匹配（店主说"两个未付款的改一个即可"）

**改成取【最近一笔】，并记录有几笔候选：**

## 五、★ 付款如何 100% 精确绑定（查完鱼麦多文档，不用备注）

**问题回顾**：我们的单号（`YMD-…`）和闲鱼单号（`XY-888`）是两套，
付款前我们不知道闲鱼单号 ⇒ 付款事件来时只能按会话 + "取最近一笔"猜。

### 查到的能力（鱼麦多开发文档 + SDK 源码）

| 能力 | 权限 | 出处 |
|---|---|---|
| ★ `order.created` 事件（买家**拍下**的瞬间，实时新单） | 订阅即可 | 文档 §4.3 订单 15 个事件之一 |
| ★ 订单**扩展字段**（挂在订单上，不改核心数据） | `order.write.extension_fields` | 文档 §4.3.3 + §4.2 |
| 订单备注（店主说不走这条） | `order.write.memo` | 同上 |
| 改价 | `order.write.price_change` ⚠️ | `reprice.mjs:145` |

**原文依据：**

```
§4.3  可订阅事件白名单 · 订单（15 个）：
      order.created、order.paid、order.shipped、order.finished、order.closed、
      order.price.changed、order.memo.changed、…

§4.3.1  order.created | orderId, accountUnb, orderStatus | rechargeOrder | 仅实时新单
        order.paid    | orderId, accountUnb, from, to        | firstSeen, …

§4.3.3  实体扩展字段（extendsEntity[]）
        "要把自定义数据挂到订单/商品上，需先在此声明字段，再用 updateExtension() 写入。
         数据落在独立的 plugin_entity_ext 表并按命名空间隔离，
         ★ 绝不改动核心订单/商品数据。"
        "未声明 extendsEntity 则不允许写扩展字段。"

§4.2    order.write.extension_fields | 写订单扩展字段 | PUT /orders/:orderId/extension
        ★ 这一条【没有 ⚠️ 高危标记】（改价/发货/取消都有）
```

**SDK 里也确认了方法存在：**
```javascript
// vendor/plugin-sdk-server/dist/client.d.ts
SetOrderMemoRequest / SetOrderMemoResult        // 备注（不走这条）
```
**唯一的坑**：`src/order-event.mjs:8` 现在只挑 8 个字段回传，
`extension` 没带上 —— **但这是我们自己的插件，改一行就行。**

### 推荐方案：订单扩展字段（不用备注）

```
① manifest 声明（两个新增）
   "subscribes": [..., "order.created"]           ← 加这个
   "extensionPoints.extendsEntity": [
       {"entity": "order",
        "fields": [{"key": "local_order_no", "type": "string",
                    "label": "本地单号"}]}]
   "permissions": [..., "order.write.extension_fields"]

② 收到 order.created（买家拍下）
   → payload 里有 orderId
   → 我们在会话里找到那笔待付款的万达单
   → PUT /orders/{orderId}/extension  {"fields": {"local_order_no": "YMD-…"}}

③ 收到 order.paid（付款）
   → 插件把 extension 一起回传（改 order-event.mjs 一行）
   → 我们直接按 local_order_no 精确命中，完全不用猜
   ★ 万一 extension 拿不到 → 回落到现在的"取最近一笔"
```

### 备选方案（都不用改 manifest 之外的东西）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 订单扩展字段** | 上面那套 | ★ 推荐：低危权限、命名空间隔离、不碰核心数据 |
| **B. 按 orderId 反查会话** | 插件已有 `im.session.read` → `GET /im/sessions/by-order` | 可取，但要确认 HTTP 方法（`GET` 带 body 不如 `PUT` 干净） |
| **C. 插件侧内存映射** | 收 `order.created` 时记 `orderId → chatId`，付款时直接给 | 最省事，但插件重启丢映射 |
| **D. 现状（取最近一笔）** | 已实现，店主已确认够用 | 兜底，永远保留 |

### ★ 我的建议

```
做 A（主）+ D（兜底）：
   A 成功 → 100% 精确
   A 任何一步不可用（没声明/写失败/扩展读不到）→ 自动回落 D，不会卡住
★ B/C 不用做 —— A+D 已经覆盖，多一条路多一处要维护。
```
