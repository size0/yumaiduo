## 三、★★ 我在 `price_capped` 上写错了一次（而且不报错）

```python
# 我第一版
capped = str(getattr(fb, "price_capped", "") or "")
"fallback_capped": capped != "不启用限价"
```

**而 `price_capped` 是布尔**（前端 radio 的 `values=[True, False]`）：
```
True  → "True"   ≠ "不启用限价"  ⇒ True   ✓ 碰巧对
False → "False"  ≠ "不启用限价"  ⇒ True   ★ 错！
```
**⇒ 配成"不启用限价"时，代码仍然当成"启用限价"。**
`maxPrice` 会悄悄从 `None` 变成有值 —— **不报错、不抛异常，只是限价悄悄生效了。**

**⇒ 修：按真值判**（同时兼容字符串形态）。
**★ 而且我给断言也踩了同一个坑**：我写
```python
check("默认 price_capped=启用限价", d...price_capped == "启用限价")  # 永远 False
```
—— 拿**显示文本**去比**布尔值**。

> **★ 教训**：`radio` 的 `options`（显示文本）和 `values`（真值）**是两回事**。
> 用 `str()` 去比中文 label，等于把类型信息抹掉 —— 而且抹掉之后
> **两个分支看起来都能跑**，只是结果永远偏向一边。

## 四、我的理解（要请店主确认的一点）

```
enabled=开（默认） ⇒ 没规则命中时照成本报（现在就是这样，行为不变）
enabled=关         ⇒ **不报价**，给买家一句"稍等，我再确认下"
mode               ⇒ LIMIT（预估）还是 FIXED（一口价）
price_capped       ⇒ 要不要那个兜底限价（不启用 ⇒ maxPrice=None，钱上不封顶）
```

**★ 只有 `enabled` 这一条是我的推断**：
我把它理解成"没有规则命中时，要不要也照成本报一个价"。
**理由**：它得有点可关的东西 —— 模式和限价已经被另外两个管了。
关掉的效果是"不报"，让规则没覆盖的场景**明确失败**，
而不是悄悄按成本卖（可能白干甚至亏）。

**★ 所以我把它做成**：关掉 ⇒ 明确不报价 + 一句给买家的解释
（不是静默少赚，也不是甩错误）。
