## 一、本地测试方法

### 1.1 官方文档说的（鱼麦多插件开发者指南 §9.1）

```
· Manifest 校验：本地起插件进程时，自注册接口会用与平台注册同一份规则
  把 manifest 错误字段逐条回执
· 插件侧逻辑自测：用示例插件自带的 mock-webhook.mjs 灌一条签名事件，
  验证验签、事件解析、关键字匹配与幂等 —— 全程无需平台参与
```
★ 我们仓库里**没有** `mock-webhook.mjs`（那是官方示例插件带的）。

### 1.2 我们自己的等价工具

| 工具 | 干什么 |
|---|---|
| `chat.py --live --chat X` | 交互式；**`/img <URL>` = 买家发选座截图** |
| `chat.py`（不加 --live） | 同上但注入假 api —— 不花钱、不下单 |
| `simulate2.py --only 问价` | 批量回放线上真实买家消息 |
| `simulate_ctx.py` | 带上下文的短回复（"1"、"2张"、"改价吧"） |
| `replay_case.py` | 回放真实案例（识别结果用线上真 payload） |

### 1.3 ★★ 这次踩到的关键约束

```
① 图片可访问性
   alicdn 直连 → HTTP 420（反爬）；带浏览器 UA → 200
   ★ 但良票识别是【它侧抓图】（文档：「模型侧直接读取，平台不下载」），
     实测它能抓到 —— 我们不用自己下载

② 桥（8000）只绑 127.0.0.1，且服务器【禁了 SSH TCP 转发】
   → Windows 上做 -L 隧道，连接立刻被 reset
   ⇒ 结论：桥相关探针【必须在服务器本地跑】

③ 良票识别要【应用签名】
   裸 urllib 会拿到 100002「缺少签名请求头」
   ⇒ 探针里自己实现：
      X-Sign = hex(HMAC-SHA256(appKey + ts + nonce + body, appSecret))
      算签名和发出去必须是【同一个 body 字符串】
```

## 四、场次定位

**★ 万达 `by-cinema` 不返回顶层片名，片名在 `showtime.filmList[].filmName` 里。**

```
摊平 187 个场次（该影院全部影片 × 全部日期）
筛「生化危机」→ 20 场，其中 8号激光厅的：
    103192878  10-14 10:50
    103184471  10-14 12:40   ← ★ 命中截图那场
    103184479  10-14 14:30
★ 时间字段是 showtime.realtime（毫秒时间戳），不是 showTime
★ 日期要按 showtimeFilmDateInf[].date 过滤（YYYYMMDD 整数），
  showDate 参数上游会忽略（早前实测：传 1999-01-01 仍返回同样的 6 天）
```

## 五、座位图：验证「W+会员座」判据

```
GET /api/showtime/seats?cityId=187&cinemaId=1183&showtimeId=103184471&phone=…

realtimeSeats 键：isRefresh / version / areaRule / area /
                 maxOrderTicketsCount / maxAutoSelectCount /
                 maxHallcolcnt / maxHallrowcnt / centreX / centreY / ticketStatus

payMemberStr = 「您还不是W+会员，开场前2小时内才可选购此座位哦」
```

### 5.1 ★★ 每个分区的两个价格（这组数字很关键）

| areaId | 区域名 | `areaPrice.salesPrice` | `wPlusActivity.price` | 座位数 | **会员座数** |
|---|---|---|---|---|---|
| 36 | W+专享 | 3590 | **3400** | 8 | **8** ← 全部 |
| 33 | 特惠区 | 3490 | **3400** | 23 | 0 |
| 32 | 优选区 | 3590 | **3400** | 96 | 0 |
| 1 | 普通区 | 3490 | **3400** | 54 | 0 |

**★ 三个结论：**

```
① 会员座判据成立：payMemberSeatStatus==1 的【只有 W+专享区那 8 个】
   特惠/优选/普通区全是 0 —— 但它们【也有】 wPlusActivity.price
   ⇒ 所以"有 wPlusActivity"不能用来判断会员座（这一点早前就验证过，这次再确认）

② ★ wPlusActivity.price 四个区【都是 3400】，而 salesPrice 分两档（3590/3490）
   ⇒ 说明 wPlusActivity 是【全店统一的 W+ 会员折扣价】，
     不是"按区域定价"。区域差异体现在 salesPrice 上。

③ 我们选的两个座位确实在 W+专享区：
     7排12座  areaId=36  payMemberSeatStatus=1  seatId=53899719
     7排13座  areaId=36  payMemberSeatStatus=1  seatId=53899717
```

### 5.2 成本

```
会员价 3400 分/张 × 2 张 = 6800 分 = 68.00 元
（原价口径 salesPrice 3590 × 2 = 7180 分）

★ 我们的取价逻辑：取【座位所在区域】的 area[].wPlusActivity.price
  座位在 areaId=36 → 3400 ✓
★ 安全校验也过：3400 < 3590（会员价不高于原价）
```

### 5.3 截图上的 ¥35.9 怎么解释

```
截图图例里 W 标记写的是 ¥35.9，而座位图给的会员价是 ¥34.00。
★ 差异原因：图例那个 35.9 是【该场次 W+专享区的 salesPrice】（3590），
  而 W+ 会员实际成交价是 wPlusActivity.price = 3400。
★ 这两个数在万达的界面上可能显示成不同位置（图例 vs 座位标签）。
★ 我们的口径：按 wPlusActivity.price 算成本 —— 那是我们实际支付的价。
  ★ 这条口径之前本地实测过：与 wplus-price 接口在 6 个场次上完全一致。
    （这次想再交叉验证，但 wplus-price 需要 seat_ids 参数，形态我没探对，
      返回 422，所以这次没验成 —— 留个待办。）
```

## 九、链路全景（这次实测确认的）

```
买家发万达选座截图
   ↓ 良票识别（应用签名）           → cityCode / cinemaId / showId / 座位
   ↓ /api/cinema/wanda-lookup      → wandaCityId / wandaCinemaId（843 条人工映射）
   ↓ /api/auth/internal/wplus-accounts → 挑一个可用账号
   ↓ /api/showtime/by-cinema       → showtimeId（按 filmList[].filmName + realtime 定位）
   ↓ /api/showtime/seats           → area[].wPlusActivity.price = 进货价
   ↓                                 seat[].payMemberSeatStatus==1 = 会员座判据
   ↓ 报价规则算售价
   ↓ 落本地单（payment_state=UNPAID，不猜付款）
   ↓ 鱼麦多 order.paid → 确认付款
   ↓ 店家在出票系统手动出票
   ↓ POST /api/order/deliver → 自动把票码发给买家
```
