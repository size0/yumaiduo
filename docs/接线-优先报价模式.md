# 接线：「优先报价模式」

> 日期：2026-10-14
> 这是接的第 15 个摆设控件（58 → 13）
> 语义由店主一句话定：
> **"现在我们设计的报价规则就是简易报价规则，专业报价规则更加复杂，我没有设计"**

---

## 一、这个控件原来是什么

设置页「识别报价」里有一个**可拖动的清单**：

```
优先报价模式   ① 简易报价规则   ⠿
               ② 专业报价规则   ⠿
               ③ API报价规则    ⠿
               ④ 比价模式       ⠿
```
**它标着「未接线」** —— 能拖、能存，但没有任何代码读它。

**★ 查证结果**：这 4 个词在 **V5 的源码里是 0 处**（我用脚本搜过整个 V5 快照）。
⇒ 它们不是从 V5 继承的语义，是**界面上的新设计**。
⇒ 所以含义只能由店主定，**不能猜**。

---

## 二、定下来的语义

| 模式 | 状态 |
|---|---|
| **简易报价规则** | ✅ **已实现** —— 就是我们现有的那套（6 条规则按 weight 降序匹配）|
| 专业报价规则 | ⬜ 未实现（店主说"更复杂，我没有设计"）|
| API报价规则 | ⬜ 未实现 |
| 比价模式 | ⬜ 未实现 |

**⇒ 这个控件的作用是【决定用哪一套规则】**：
取清单里第一个「已启用 **且** 已实现」的模式，用它的规则集报价。

因为现在只有一种模式，而它 = 全部规则，
**所以接线前后是同一批规则、报价逐分不变。**

### ★ 为什么不直接删掉那三个

删了以后没人知道曾经规划过这几条路；而且以后做「专业报价」还得把界面加回来。
**标着「未实现」才诚实。**

## 三、改了什么

### ① domain：新增模式表和筛选函数（纯函数，不读配置）

```python
MODE_SIMPLE = "简易报价规则"
MODE_RULES = {MODE_SIMPLE: None}      # None = 全部规则（现在唯一实现的）

def select_rules_by_priority(rules, priority) -> (规则, 模式名, 说明)
```
**四条规则（都有测试盯着）**：
```
① 按清单顺序找第一个 enabled 且 implemented 的模式
② 一个都没有 ⇒ 返回【全部规则】+ 说明
   ★ 不返回空规则集：那会让所有报价掉进兜底（按成本卖）——
     "静默少赚"最典型的形态。我特意测了这条。
③ 命中的模式是 None ⇒ 全部规则
④ 未实现的模式即使排在最前且 enabled 也被跳过（不能假装支持）
```

### ② settings：标出哪几个实现了

```python
implemented=["简易报价规则"]      # 新增元数据
```
配置页据此把其余三个显示成「未实现」并禁止拖动/启用。

### ③ 接进报价链路（两处，共用同一个辅助函数）

```
application/service.py   build_service 里筛规则
server.py                另一条构造路也筛
application/service.py   _quote_priority(cfg)  ← 唯一读配置的地方
```
**★ 逻辑只写一遍**：`server.py` 复用 `service_mod._quote_priority`，
两处各写一遍早晚会不一致。

### ④ 界面

```
config.js  sortable 渲染器：未实现的 → 虚线 + 无手柄 + 「未实现」标签 + 不可拖
config.js  collect      ：未实现的不会被存进配置（兜一道）
config.css .sortable-item.not-impl 样式
```
**★ 视觉上必须和「已实现但被停用」区分开**：
```
已实现但停用 = 实线 + 透明度低      ← "我能打开它"
未实现       = 虚线 + 「未实现」标签 ← "它根本还没有"
```
两者含义完全不同，用同一种视觉会让运营分不清。

## 五、★★ 这次差点又假通过一次

我第一版给元素的写法是：
```javascript
el('div', { draggable: ok ? 'true' : 'false', ... })
```
而 `el()` 对非白名单键做的是**属性赋值** `node[k] = v`。
`node.draggable = 'false'` —— **字符串 `'false'` 是真值** ⇒ 元素变成可拖动。

**⇒ 结果：四个模式全都能拖。** 而我的断言是：
```python
check("未实现项不可拖动", "draggable: ok ? 'true' : 'false'" in _js)   # ← 假通过
```
**它只检查源码里有那行【字】。** 源码里有那行字，行为和它对不上。

**这是我这几天同一个毛病的又一次**：断言扫源码 ⇒ 扫到自己写的解释文字/看着对的字面量。
**改法两步**：
```
① 实现改成 `if (ok) item.setAttribute('draggable','true')`（不给就不设）
② 顺手把 el() 的 draggable 当【布尔属性】处理（堵住这条路）
③ 断言改成检查【实现方式】：必须用 setAttribute + 必须有 el() 的布尔处理
```

**★ 教训**：断言"源码里有某行字"≈ 没断言。
能验行为就验行为（computedStyle / innerText / 真拖一下），
验不了才退而求其次验实现方式 —— 但绝不能只验字面量存在。
