## 二、★ 挂在哪个定时器上（这决定了要不要新起进程）

查到了**现成的**：插件**每秒**调一次 `POST /api/v1/events/run-due`
（`server.mjs` 的 `readingDue` 定时器）。
提醒就是"到点了没有"的检查 ⇒ 挂在这个 tick 上，**不需要新进程、新定时器**。

**但那条路的注释明确写着**：「它必须便宜：没事件时立刻返回」。
所以 `run_reminders()` 做了两层节流：
```
① 一个提醒都没启用 ⇒ 连订单都不读，立刻返回
② 距上次扫描不到 30 秒 ⇒ 直接返回（提醒精度是"分钟"，每秒扫是白烧 IO）
```

## 三、全新模块 `application/reminders.py`

**设计成纯函数**（订单和配置都可注入）⇒ 可单测、不读盘、不建队列：

```python
def build_reminder_commands(*, now=None, orders=None, cfg=None) -> list
```

**幂等靠 `dedupe_key`**：`reminder:<类型>:<订单号>`。
队列的 `enqueue` 会按这个键去重 ⇒ 同一单同一提醒只发一次。
★ **不靠内存标记** —— 重启/多进程下内存标记会漏。

**加一个提醒 = 加一行**（数据驱动）：
```python
REMINDERS = (
    ("movie_remind", r_movie_remind, None),
    ("urge_receive", r_urge_receive, None),
    ...
)
```

## 四、★★ 两个我踩的坑

### 坑 1：场次时间是「影院的本地时间」，不是 UTC

```
订单里写的是「2026-10-20 19:30」——
这是【北京时间】，不是 UTC。
我原先把解析结果无条件当 UTC ⇒ 在北京算窗口偏 8 小时
⇒ 观影提醒永远不会在正确的时刻触发。
```
**修法**：统一规则 —— naive 时间按**本地时区**理解，比较前两边都转成 naive 本地。
不做跨时区换算（影院和系统在同一地）。

**另外一条**：场次**解析不出来就不发**，不兜底成"现在就发"。
在错误的时刻发观影提醒比不发更糟（买家以为记错了场次）。

### 坑 2：我的测试假设了错误的默认值

```
我假设 advance_minutes=60 / urge_order.delay_minutes=30
实际默认是         10 /                    60
⇒ 两条断言全挂，我一度以为代码坏了。
```
**教训**：测试要**显式给出前提**，不依赖默认值。
否则以后调默认值会让测试挂掉，而那时功能其实没坏 —— 白查一场。

**还有一条同类**：测试里的 `mk()` 默认 `payment_state="CONFIRMED"`，
而我用它造了一个"还没拍下"的订单 ⇒ `r_urge_order` 正确地不催它
（已付款不该催下单），但我的断言期望它催。**又是前提没给全。**
