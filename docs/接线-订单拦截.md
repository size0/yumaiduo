## 一、★ 查到的语义（每一环都有依据）

```

      "订单拦截（取消）"  ⇒ **拦截 = 取消订单**
② 插件已有 CLOSE_FAILED_ORDER 命令（failed-order-close.mjs），
   它做的就是取消闲鱼订单，而且带足了安全：
      · 只在 live 模式真做（shadow 只返回 WOULD_SEND）
      · 校验订单身份（orderId + accountUnb 都要对上）
      · 只允许【已付款未发货】(orderStatus 2/6) —— 发货后绝不关
      · 要后端 /authorize-close 授权，且逐字回核字段
      · 注释写明 "Never replay a cancel write"（取消不许重放）
③ 订单上存着【平台订单号】（下单时从平台事件里取的 online_order_id）
```
**⇒ 接线方式明确：买家说拦截 ⇒ 回那句话 + 发一条 `CLOSE_FAILED_ORDER`。**

**★ 所以这里也是"接线"而不是"实现功能"** —— 命令、授权、安全判据全都在，
缺的只是"谁来触发它"（和 `ch5_cancel` 一样，之前只在注释里出现过）。

## 二、接了两条

### ① 手动拦截：买家说「拦截订单」

**走确定性路由**（和"获取票码"同一个理由）：
```
order_intercept.keyword 是一个【指令】（默认"拦截订单"），
而且配了一句写死的话术 ⇒ 这是"逐字可控"那条路。
★ 而"拦截"要动订单，更不能让模型自由发挥。
```
**★ 只认【精确等于】**（`want == kw`）：
包含匹配会让「拦截订单**要多久**」这种**询问**也命中 ——
而这条会**真的去关单**，绝不能误判。
（实测：「拦截订单」→ 走拦截；「拦截订单要多久」→ 走模型 ✓）

**★ 位置**：确认指令之后、关键词之前 —— 和取票码同级。

### ② 自动拦截：买家申请退款时顺手拦

**落点**：`on_refund_request` 里 `REFUND_APPLIED` 之后的同一段。
```
★ 语义：票还没出就把单拦掉，比"出了票再退"省事得多
        （退款要手续费、买家还要等）。
★ 放在 REFUND_APPLIED【之后】—— 拦截失败不该影响"退票已受理"这个结论。
★ 默认 enabled=False ⇒ 默认行为一个字不变。
```

## 三、★★ 一条关键安全判据：没有平台订单号就不发关单命令

插件的 `CLOSE_FAILED_ORDER` 会做：
```javascript
const detail = await cfg.client.orders.get(command.order_id);
if (!same(detail)) return fail('CLOSE_ORDER_IDENTITY_MISMATCH');
```
**⇒ 订单号是空的话，必然被身份校验拒掉。**
发出去只是**浪费一次调用 + 留一条失败记录**。

**⇒ 所以两条路都先判**："有平台订单号才发"。

**★ 但仍然回那句确认话术** —— 因为买家要的是"**我提了**"这个确认，
而且配置里的话术自己就写着「**不保证拦截成功**」。
**★ 我原样用那句话术，没有改成"已为您拦截成功"** —— 那是骗人。

## 四、★ 三条不猜的取舍

| 取舍 | 做法 | 理由 |
|---|---|---|
| 匹配方式 | **精确等于** | 含义是"关单"的动作，误判代价大 |
| 没订单号时 | **不发命令，但仍回话** | 发了必被拒；买家要的是确认 |
| 话术 | **原样用配置**（不改成"成功"） | 配置自己写了"不保证成功" |
| 幂等键 | `intercept:<平台单号>` / `auto_intercept:<平台单号>` | 买家反复说"拦截"不该反复关单 |
