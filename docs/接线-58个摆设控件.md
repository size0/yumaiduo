## 一、先回答「无法保存修改」是什么

我实测了三种情况，结论是**后端保存一直是好的**，症状有两个来源：

```
① 开关 / 单选 / 多选  → 我把未接线的【真禁用了】⇒ 点不动
                        ⇒ 你的感受是"改不了"
② 文本框 / 数字框      → 能改、能存进 data/settings.json
                        但没有任何代码读它 ⇒ 你的感受是"保存了也没用"
```

**实测证据**（改一个未接线的文本框）：
```
改前 recognize_quote.keyword_cinema = '影院'
改后 recognize_quote.keyword_cinema = '影院XYZ'   ← 确实存进磁盘了
⇒ 能存进去（但没人读）
```
而**已接线的**那个（放映剩余分钟 40 → 77）点保存后提示"已保存 ✓"、重载还是 77。

**⇒ 两个症状是同一个病根：那 58 个没接线。** 不是保存机制坏了。

（顺带排掉一个嫌疑：控制台那个 404 是 `favicon.ico`，浏览器自动请求的，
逐页查过 9 个页面都没有真实资源缺失。）

## 二、★★ 接线时我犯了一个真错误（值得记）

```
我把「订单发货 → 强制发货开关」接到了发货闸门的付款判断上，
让"未付款也能发货"。
```

**错在两点：**
```
① 那行代码的注释写着「未付款的不发（钱没到手就发货，钱收不回来）」
   —— 这是钱上的硬闸门，我不该让一个界面开关绕过它。
② force_ship 的【默认文案】说明了它真正的语义：
   「收到您的退款申请后…已自动出票…小店已为您转为正常发货」
   ⇒ 它管的是【退款拦截失败后仍转正常发货】，
     不是"允许未付款发货"。
```

**回归用例当场抓住了**（原本 2 条发货命令变成 4 条），我撤回了改动并把付款闸门恢复原样。

**★ 教训：接线前必须读【开关的默认文案和周边注释】，
不能只看 label 猜语义。** 这次是靠原有回归用例兜住的 ——
如果没有那两条断言，这个错误会变成"钱没到手就发货"。

## 三、已验证接线的 3 个（58 → 55）

| 开关 | 接在哪 | 关掉之后 |
|---|---|---|
| `amount_check.verify_amount` | `ledger.confirm_payment` | 金额不符时：记差异但放行（原来一律拒绝） |
| `fish_reprice.auto_reprice` | `plugin_runtime._from_order_card` | 只绑闲鱼订单号，不排改价命令（转人工） |
| `order_ship.auto_ship` | `plugin_runtime.queue_shipping_for_delivered` | 不自动排发货命令（等人工发货） |

**每一个都做到了三件事：**
```
① 默认值不动 ⇒ 默认行为与接线前完全一致
② 读不到配置时 fail closed ⇒ 按最严的来（不改价放行/不误发）
③ 关掉之后【仍然记录事实】⇒ 不是"关了就瞎"
   例：verify_amount 关掉后，金额差异照样写进 payload.amount_mismatch
```

**验证方式**：不只读源码（那只能证明"写了 if"），而是
`settings.load()` 每次读盘无缓存 ⇒ **真改配置、真跑那段代码、看行为变没变**。
