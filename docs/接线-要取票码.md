## 二、接了什么

**在 `on_message` 里加了一条确定性路由，位置在"确认指令"之后、"关键词回复"之前**：
```
为什么放这里（顺序有讲究）：
  · 它在语义上是一条【指令】，和"正确"同级 ⇒ 不该被关键词吃掉
  · 但也不能抢在确认指令前面（确认要花钱，优先级最高）
```

**语义**：
```
买家说的话 == 配置的关键字（精确等于）
  · 有已出票的单 ⇒ 把取票码发给他
  · 没有         ⇒ 回 no_ticket_reply
```

**三个不猜的取舍**：

| 取舍 | 做法 | 理由 |
|---|---|---|
| 匹配方式 | **精确等于**（照 `_is_confirm`） | 包含匹配会让「我获取票码了吗」这种**询问**也命中 —— 那该让模型答 |
| 查账方式 | `orders_payload()` 按 `chat_id` 过滤 | `by_identity` 要身份四元组，而 `Conversation` 上只有 `chat_id`；`orders_payload` 是订单页也在用的**同一条读模型** |
| 过滤条件 | 排掉 `CANCELLED/REFUNDED/FAILED` 的单 | 那些单的票码**已作废**，发出去会让买家白跑一趟 |

**实测**：
```
'获取票码'      → '您还没有出票成功的订单~'   ✓ 走确定性路由
'获取票码了'     → 走模型（怎么取票那句）      ✓ 询问没被指令吃掉
'我获取票码了吗'  → 走模型                    ✓
'人工客服'      → 走模型（不受影响）          ✓
```

**★ 不改变会话状态** —— 它是旁路查询，不是流程推进（和关键词回复同一性质）。


**★ 所以那条界线要再补一句**：
```
"需要新增控制流" ≠ "实现功能" ——
  如果新增的控制流是【照已有的形状组合已有能力】，
  而且语义在配置/注释里有依据，那它就是接线。
```
