## 三、部署过程中踩的坑（都很典型）

### ① 我改了代码，新加的防护自己变成崩溃源

```javascript
// 我加的第一个版本
function buildClient(token) {
  if (!token || !TENANT_ID) return null;      // ← 没检查 coreUrl
  return createPluginClient({ coreUrl: process.env.CORE_URL, ... });
}
```
**没有 `CORE_URL` 时**（影子跑、本地自测、`npm test`）SDK 内部
`.replace()` 抛 `TypeError` ⇒ **进程启动就崩**。

**★ 教训**：新增的"守卫条件"必须覆盖**它依赖的全部输入**。
我检查了两个、漏了第三个。

**已固化成断言**（`test/acceptance.mjs` 的 4.5 组）：
```
[PASS] 没有 CORE_URL 时进程仍然存活（不崩）
[PASS] 没有 CORE_URL 时 /healthz 仍可访问
```

### ② 手工起后台进程不可靠

我用 `sudo bash -c '... nohup node ... &'` 起了三次，两次进程根本没活下来，
而且没留下日志（重定向和 sudo 的作用域搅在一起）。

**⇒ 改用 systemd。** 这也顺带解决了重启自愈和日志可查。

### ③ 降权运行和"读 root 的 env"是冲突的

```
/etc/ticket-system-v5/plugin.env   0600 root:root
launcher 以 ubuntu 跑  ⇒  Permission denied  ⇒  所有变量都没加载
                       ⇒  自注册报 MISSING_ENV: CORE_URL, PLUGIN_DEVELOPER_TOKEN
```
**修法**：launcher 以 root 读 env，然后用 `setpriv --reuid=ubuntu` **降权执行 node**。
（systemd 的 `EnvironmentFile=` 也是这个模式：root 读、服务进程降权。）

**★ 为什么不干脆把那个 env 文件放开权限**：里面有 `PLUGIN_DEVELOPER_TOKEN`
和 `YUMAIDUO_WEBHOOK_SECRET`。放开等于把平台凭证给机器上所有用户。

### ④ 中文注释里的括号会打断 bash 脚本

我在 heredoc 的中文 echo 里写了 `（` `）`，bash 报
`syntax error near unexpected token '('` —— **而且脚本是执行到一半才断的**，
前半段生效、后半段没跑（所以服务"看起来装了却没启动"）。

**⇒ 脚本里的中文提示改成不含括号；复杂脚本用文件传，不要内联。**

## 四、回滚（1 分钟）

```bash
# ① 停我们的插件
sudo systemctl stop ticket-agent-plugin && sudo systemctl disable ticket-agent-plugin

# ② 恢复插件 env + 起 V5 的插件目录
sudo cp /etc/ticket-system-v5/plugin.env.bak-before-own-plugin /etc/ticket-system-v5/plugin.env
sudo systemctl enable --now ticket-system-v5-plugin

# ③ 后端 env 恢复（把 YUMAIDUO_WEBHOOK_SECRET 打开）
cp /home/ubuntu/ticket-agent.env.bak-before-own-plugin /home/ubuntu/ticket-agent.env
sudo systemctl restart ticket-agent
```

**★ 注意**：V5 的静态令牌还是被撤销的那把，回滚只能恢复到"插件收得到事件、
但调不了平台 API"的状态。**回滚的意义是"万一我们的插件把事件处理坏了"**，
不是"恢复到 V5 能干活"（它已经不能干活了）。

## 六、这次真正学到的一件事

**我之前把"插件能收到事件"当成了"插件是好的"。**

实际上那是两条独立的路：
```
平台 → 插件（webhook 入站）    靠 webhookSecret 验签      ← 一直是好的
插件 → 平台（调 API 干活）      靠 yp_ 令牌               ← 一直是坏的
```
前者好，让人以为后者也好。**而"能收消息"恰恰是客服系统里最没用的能力 ——
真正的活全是出站 API（发消息、改价、发货）。**

⇒ 验收必须打在**真正会坏的那一环**上。
这也是为什么我在 `test/acceptance.mjs` 里专门断言
"平台收到的是【新令牌】、且【没有】收到旧令牌" ——
只测"能启动、能收事件"的话，那个坏掉的版本会全部通过。
