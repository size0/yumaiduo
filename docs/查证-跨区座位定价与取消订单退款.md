> 日期：2026-10-14

## 一、★ 先纠正我自己的一个错误推论

**我一度认为根因是「maxPrice 按均价算，低于跨区时的限价上限」。这个推论是错的，真接口实测推翻了它。**

### 我当时的推理（错的）

```
文档 1182：maxPrice 总限价(分，数字)。【实际应付超过时下单失败，报 300005】
文档 1183：areaQuoteStrategy  AVERAGE(默认，按实) / HIGHEST / LOWEST
文档 1088：跨分区时平台按每个座位所在分区逐座计价

我实测（场次 38208129，最贵区 4990 + 最便宜区 4290 各一座，LIMIT）：
   AVERAGE  total=8697  estimate=7509
   HIGHEST  total=9353  estimate=7509
   LOWEST   total=8041  estimate=7509

我们的算法：maxPrice = (cost_unit + limit_yuan) × 张数
            cost_unit 来自 estimateAmount = 7509/2 ≈ 3755
            ⇒ maxPrice = (3755 + 50) × 2 = 7610

我的结论：7610 < totalAmount(8697~9353) ⇒ 下单会被 300005 拒
```

### 真接口实测（推翻它）

用 4990 区 + 4290 区各一座，**老算法算出的 maxPrice=7608**，直接调 `/order/create`：

```
POST /order/create  priceMode=LIMIT  areaQuoteStrategy=AVERAGE  maxPrice=7608
→ code=0  success
→ orderNo=LP20261014070615WQ5AQV7N  freezeAmount=7608  status=SUBMITTING
```

**⇒ `maxPrice` 判的是【实收金额】（按分区逐座算出来多少），不是 `totalAmount` 那个限价上限。
老算法按 `estimateAmount`（预估应付）+ 限价，本来就 ≥ 实收，不会触发 300005。**

★ 顺带纠正另一个观察误差：我先前"不传 `areaQuoteStrategy` 时 total=9353"，
和"文档说默认是 AVERAGE"矛盾 —— 那是我没传时的平台默认配置行为，
**不能拿来当算法依据**。显式传 AVERAGE 时 total=8697，与文档一致。

## 二、`freezeAmount == maxPrice` 这个实测发现

```
orderNo=LP20261014070615WQ5AQV7N  maxPrice=7608  freezeAmount=7608
```

**⇒ LIMIT 模式下冻结额就等于 maxPrice。** 于是：

```
把 maxPrice 抬高 ⇒ 只是白冻更多余额（结算后会退），没有任何收益
                  ★ 而且冻结期间那部分余额不能用（占额度）
⇒ 只要 maxPrice ≥ 实收就够了，不该为了"保险"抬高
```

**所以我最后【没有改钱】，把算法恢复成原样。**

## 四、以及店主问的第一件事：取消订单会不会退款

**你说「取消订单就是关闭订单了，会给买家退款的」。**

我核了 `yumaiduo-plugin-developer-guide (9).md`（最新版，300 KB）：

```
· 「取消订单」对应的就是 POST /orders/:orderId/cancel（scope order.write.cancel）
  CancelOrderRequest 只有 reason 一个必填字段（1~200 字，写入订单事件与审计）
  ★ 文档里【没有】任何一句说它不退钱
· 全文只有一处讲"平台自动向买家退款"：
    order.write.recharge  直充订单充值状态推进（fail 会触发闲鱼【自动向买家退款】）
· 退款决策是另一套：GET /orders/refunds/:refundOrderId（order.refund.read）
                 POST /orders/refunds/:refundOrderId/agree|refuse
                 （order.refund.decide，★ 这个权限我们没声明）
```

**⇒ 文档既没证实也没否定"cancel 会退款"。**

**★ 我按你的业务判断来实现（你运营这个店，你的判断优先于我读文档的推断）：**
- 关单命令已经接通（`CLOSE_FAILED_ORDER`，见 `docs/改造-关单链路与跨区定价根因.md`）
- 如果 cancel 确实退款，那"自动退款"这件事**已经做到了**，不需要再加 `order.refund.decide`
- `order.refund.decide` 只在"买家主动申请退款、要卖家同意"时才需要 ——
  那是另一条路（买家发起），不是我们关单这条

**★ 但这有一个可验证的判据**：下次真的关一张单，看
`PluginRefundView.refundStatus` 走不走到 `5`（退款成功）。
走到 5 就说明 cancel 会退款。**在没验证之前，我不会在文档里写死"cancel 会退款"。**
