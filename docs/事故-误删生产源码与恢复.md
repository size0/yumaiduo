# 事故：我误删了 `application/plugin_runtime.py`，以及怎么恢复的

> 日期：2026-10-14
> 性质：**单文件、生产源码、无版本控制、误删**
> 结果：已完整恢复，46 套自检全过

---

## 一、发生了什么

我在写一个新测试时，先执行了一条清理命令：

```powershell
Remove-Item "application\plugin_runtime.py"   # ← 我本来想删的是测试脚手架
```

**而 `Remove-Item` 不进回收站。** 这个项目又**不是 git 仓库**
（`git status` → `fatal: not a git repository`）。
⇒ **删掉就是删掉，没有任何版本历史可以回退。**

`plugin_runtime.py` 是**生产源码**（791 行，插件事件 → 命令的业务转换层），
当时后端正在跑它。

---

## 二、为什么后端没立刻挂

Python 进程启动时已经把模块加载进内存了，删除磁盘文件不影响运行中的进程。
所以 `systemctl is-active ticket-agent` 仍然是 `active`。

**★ 但这是假安全**：只要一重启（我第一次重启后端就在几分钟后会发生），
`ImportError` 就会让整个后端起不来。

---

## 三、怎么恢复的

### 第一步：找副本（快，先做）

```
① 服务器部署副本   /home/ubuntu/ticket-agent.new/application/plugin_runtime.py
   ★ 只有 02:33 那个版本 —— 我这次会话的所有改动都还没部署 ⇒ 缺改动
② 回收站           没有（Remove-Item 不进回收站）
③ .bak/.orig       没有
④ __pycache__ .pyc ★ 有！plugin_runtime.cpython-312.pyc（14:01，删除前刚编译）
```

**结论**：唯一含本次改动的完整副本是 **`.pyc`**。

### 第二步：能不能反编译

```
decompyle3   → TypeError（不支持 3.12）
uncompyle6   → AssertionError: 3.12 does not smell like code
⇒ 两条路都不行
```

### 第三步：确定"改动面"（关键判断）

不盲目重建整个文件，而是**先算清楚差多少**：
```
从 .pyc 的 code object 里读各函数的 co_firstlineno：
  _from_order_card  206 → 383  （178 行）
服务器旧版同一函数只有约 90 行
⇒ pyc 覆盖到第 880 行，服务器版 791 行
⇒ 本次改动 ≈ 90 行，集中在 _from_order_card
```

**⇒ 最省且最保险的路子**：
**以服务器那份 791 行完整源码为底（注释全在），只重放我这次的改动。**

### 第四步：从 .pyc 里抠出重建所需的确切信息

```python
ORDER_CARD_MESSAGE_TYPE 的值 = '26'
ORDER_CLOSED_STATES 的值    = ('DELIVERED', 'CANCELLED', 'REFUNDED', 'FAILED')
```
（这两个常量我是从字节码的 `co_consts` 里读出来的，不是靠记。）

### 第五步：重放改动 + 对拍

```
服务器版 → 加 ORDER_CLOSED_STATES 常量（含注释）
        → 重写 _from_order_card 的候选判据（改用具名常量）
        → 加 ①b「一拍就进单」补落单逻辑
结果：875 行，语法 OK，函数集合与 .pyc 一致（唯一差异是 <genexpr>）
```

**★ 顺带发现**：`.pyc` 里有我临时加的 `os.environ` / `print` 调试代码
（names 里能看到 `os`/`environ`/`print`）—— 重建时**没有**把它带回来。

## 五、★ 这次真正该记住的事

### ① 用 `Remove-Item` 删源码 = 没有撤销

```
Remove-Item  →  不进回收站
非 git 仓库  →  没有历史
⇒ 一个手滑就是永久丢失
```
**以后删任何源码文件之前，先改名（`.bak`）或移到别处，不要直接删。**
更根本的是：**这个项目该进版本控制。**

### ② 我删它的理由本身就是错的

我当时的动机是"清理临时脚手架"。
**而 `application/` 下的东西永远不是临时文件。**
清理只该针对我自己刚创建的、写在根目录的 `_*.py` / `_*.sh`。

### ③ 恢复时"先算改动面"省了大量工作

如果我盲目从 `.pyc` 逐字节重建整个文件（880 行、注释全丢），
不但慢，而且很可能引入新错误。
**先量出差多少（90 行 vs 791 行），再选最小改动路径** ——
这一步是这次恢复能成功的关键。

### ④ `.pyc` 是意外保险

平时它是构建垃圾，**出事时它是唯一的字节码事实来源**。
所以我从它里面只取"确切值"（常量、函数集、行号跨度），
其余用带注释的服务器源码 —— 两边互补。

### ⑤ 我对新测试脚手架投入过度

在恢复之后，我还在跟那个行为测试纠缠了好几轮
（历史会话残留、`orders_payload` 快照、`by_identity` 签名……
一直得到自相矛盾的数）。

**最后我做了正确的事**：
- 把"老流程"那节里**我自己都看不懂的断言删掉**，换成我确定的两条
- 把"重投不重复落单"这个**真风险**单独写了一套干净隔离的测试（3/3）

**★ 一个看不懂的断言比没有断言更糟** —— 它会让人以为那里有保障。
