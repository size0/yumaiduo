### 1.3 ★ 两个容易静默失败的坑（都踩过）

**坑一：授权响应的键必须和插件回核的字段对齐，而且不能用空串补齐。**
```
failed-order-close.mjs:23 逐字比这组：
  ['command_id','type','tenant_id','shop_id','order_id','booking_order_id','text']
判据是 `键在 grant 和 command 上是否同时相等`。
★ Command 的字段里【没有】order_id / booking_order_id（只在 extra 里），
  空值也会被 to_dict 序列化出来（空串）。
⇒ 用 "" 补齐一个命令根本没有的键 → 插件判 undefined ≠ '' →
  CLOSE_AUTHORIZATION_REJECTED，而且是静默的。
⇒ 所以 authorize_close 是【按命令实际有的键】拼 grant，没复用 _identity_of。
```

**坑二：测试自己会骗人。**
```
_mk() 默认 command_id=f"c-{kind}"，同类型再造一条会命中入队去重、
拿回【第一条】。于是"测没写原因"实际测的是上一条（有原因），
断言说"没拦住" —— 是测试的错，代码是对的。
⇒ _mk 加了 cid 参数（并且 dedupe_key 也带上 cid）。
```

### 1.5 ★★ 退款这件事必须说清楚：**关单【不退钱】**

## 二、跨区座位为什么"会建单失败"—— 根因找到了

### 2.1 实测数据（真接口，只询价 /order/preflight，免费）

场次 38208129，2 号厅，4 个分区：

| areaId | 原价（分） | 可售 |
|---|---|---|
| 8810 | 4990 | 49 |
| 8811 | 4790 | 37 |
| 0 | 4490 | 26 |
| 9107 | 4290 | 1 |

选**最贵 + 最便宜**各一座（4排12座 4990 + 6排12座 4290，原价合计 **9280**）：

```
FIXED  AVERAGE / HIGHEST / LOWEST 全部 = 7673    ← FIXED 是逐座确定合计，策略无影响 ✓ 与文档一致
LIMIT  AVERAGE  total=8697  estimate=7509
LIMIT  HIGHEST  total=9353  estimate=7509        ← 最宽
LIMIT  LOWEST   total=8041  estimate=7509        ← 最窄
LIMIT  不传 areaQuoteStrategy（=我们现在的行为）→ total=9353   ← 表现同 HIGHEST
```

★ `maxPrice` 传不进 preflight（`100001 property maxPrice should not exist`），
它只属于 `/order/create`。

### 2.2 根因

```
文档 §5.1：
  totalAmount    最优应付总额(分)。FIXED 即成交价，LIMIT 为【限价上限】
  estimateAmount 预估应付(分)，LIMIT 模式参考
文档 1088：
  areaQuoteStrategy 只在座位跨分区、且 priceMode=LIMIT 时有区别，
  它决定给上游的出价上限：
    AVERAGE 按所选座位加权平均（等于逐座真实合计，默认）
    HIGHEST 按最贵分区单价 × 座位数（上限宽，更容易撮到货，可能多付）
    LOWEST  按最便宜分区单价 × 座位数（更省，可能撮不到货而出票失败）
```

**我们的代码：**
```python
# integrations/liangpiao/api.py  PreflightResult.cost_basis_fen
优先用 estimateAmount（LIMIT 的成本基准）
# domain/quote_rules.py:653
max_price = (cost_unit + limit_yuan) * seat_count      # ← 按【均价】反推单价
```

**⇒ 跨区时 `estimateAmount`(7509) 与 `totalAmount`(9353) 差 1844 分，
而我们把 maxPrice 建在均价上：**

```
仅启用规则是「兜底全院线预估」：method 动态折扣、markup 0、limit_yuan 0.5、capped True
cost_unit = 7509 / 2 ≈ 3755（四舍五入）
limit_unit = 3755 + 50 = 3805
maxPrice   = 3805 × 2 = 7610

平台要的上限 totalAmount = 9353
★ 7610 < 9353  ⇒ 下单限价不够 ⇒ 这种单【会失败】
```

**同区时不会暴露**（estimate == total，两个数相等）。
**正是店主说的"两个座位价格不一样 → 会建单失败"。**

### 2.3 修法（三条路，要店主定商业口径）

```
路线 A（最省事、最稳）：LIMIT 的成本基准改用 totalAmount 而不是 estimateAmount
  ⇒ maxPrice 自然 ≥ 平台要的上限，不会再失败
  ★ 代价：报价会变高（本例成本从 3755 → 4676.5/张）。
    但 totalAmount 是【限价上限】不是成交价 —— 实际成交可能更低，
    多出来的是我们自己的毛利空间被压缩，不是多收买家钱。
  ★ 这条最符合"必须能建单"的硬要求。

路线 B（保毛利）：按分区逐座算限价，取每座单价的最大值 × 座位数
  ⇒ 需要从座位图拿每个座位的分区价（我们已经有 areaId 和 areas[].originalPrice）
  ★ 更精确，但要改报价引擎的输入形状。

路线 C（照文档用策略）：显式传 areaQuoteStrategy=HIGHEST
  ⇒ 平台按最贵分区出价，最容易撮到货
  ★ 但它【不会】让 maxPrice 变大 —— 我们传的 maxPrice 仍然是那个均价算出来的，
    所以 C 单独用【解决不了】。必须配 A 或 B。
```

**★ 我的建议：A + 显式传 `areaQuoteStrategy`（不要靠平台默认）。**
理由：默认策略是会变的（我们现在观测到像 HIGHEST，但文档写默认是 AVERAGE，
两者不一致 —— 依赖一个我们观察不出稳定结论的默认值，等于把建单成功率押在别人的配置上）。
显式传一个我们想清楚的值，行为才可复现。

**这条要店主点头再改** —— 它动的是报价口径（成本↑ = 毛利↓），是商业决定。
