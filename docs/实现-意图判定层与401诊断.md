## 一、401 是咋回事

### 1.1 调用链（从代码读出来的）

```
V5 插件的消息读取路径：
  readOfficialMessages(body, client, tenantId, verified)     message-history.mjs:13
    ├─ 要求 verified === true    ← webhook 签名校验通过
    ├─ 要求 body.tenant_id、shop_id、chat_id、buyer_id 齐全
    └─ client.im.listMessages({accountUnb, chatId, pageSize:100})
         → GET /api/v1/plugin/im/messages
         header: x-plugin-token   ← ★ 401 就是这个头
```

```
令牌从哪来（register.mjs 全文只有这一段）：
  POST /api/v1/plugin/runtime/register
    header: x-plugin-developer-token
    body:   { manifest, baseUrl }
    ↓ 返回
  if (data.webhookSecret) cfg.secret = data.webhookSecret
  ★ ★★ 只存了 webhookSecret —— 【没有存任何 x-plugin-token】
```

### 1.2 实测（三个令牌，全部 401）

| 令牌 | 长度 | 来源 | 结果 |
|---|---|---|---|
| `YUMAIDUO_PLUGIN_TOKEN` | 51 | V5 plugin.env（静态） | 401 插件令牌无效或已撤销 |
| `PLUGIN_DEVELOPER_TOKEN` | 44 | V5 plugin.env | 401 同上 |
| `PLUGIN_DEVELOPER_TOKEN` | 44 | wanda-seat-autoquote.env（**正在跑**） | 401 同上 |

```
GET /api/v1/plugin/runtime/register → 404 "Cannot GET ..."   ← 端点存在，只是要 POST
⇒ 平台可达、服务正常，是【令牌】被拒。
```

### 1.3 结论

**那个静态 `YUMAIDUO_PLUGIN_TOKEN` 已被平台撤销。**

**而 `YUMAIDUO_AUTO_REGISTER=false`**（server.mjs:24 只在 `=== 'true'` 时才注册）
**⇒ 系统不会重新注册 ⇒ 这个 401 不会自愈。**

### 1.4 ★ 两个容易误解的点

```
① webhook 收得到消息 ≠ token 有效
   收消息靠的是本地 HMAC 校验（YUMAIDUO_WEBHOOK_SECRET），
   和 x-plugin-token 是两套东西。所以"插件还在正常工作"不代表 token 好。

② 关于鱼麦多的开发文档：网上搜不到公开文档
   （搜索结果全是无关的公司信息）。
   上面这些是我从【插件运行时源码】读出来的 ——
   register.mjs / message-history.mjs / vendor/plugin-sdk-server/dist/client.js
   如果你手上有文档链接，发我，我核对一遍有没有遗漏的续期/轮换机制。
```

### 1.5 想自己拉真实会话的话（两条路）

```
路 A（最小改动）：把 V5 plugin.env 里 YUMAIDUO_AUTO_REGISTER 改成 true
   → 重启 ticket-system-v5-plugin
   → 它会用 PLUGIN_DEVELOPER_TOKEN 去 register 换新令牌
   ★ 但前提是那个 developer token 还有效（现在看起来也被拒了）
   ★ 而且这会改 V5 的运行配置 —— 你要同意我才动

路 B（不碰 V5）：你在鱼麦多后台重新生成一个插件令牌给我，
   或者直接在闲鱼 App 里把买家消息复制出来给我（我只要 20~30 条短消息）
```

## 二、放宽确认 —— 做了，而且做成了意图层

### 2.1 我放弃了原来那个想法

我原本准备写"长度阈值 + 疑问词排除"的启发式。**想清楚之后否掉了**：
那等于再写一层关键词库（换汤不换药，还是漏），而且规则会互相打架
（「行吧」是同意还是不满？）。**判意图恰好是模型的强项**，所以这一层交给它。

### 2.2 结构

```
on_message 判路顺序（我插了 5.5）：
  1. 图片 → 识别
  2. 候选序号 → 二次确认
  3. ★ 逐字确认指令（最优先，不动）
  4. 关键词（25 条）
  5. "付好了"这类启发式（不动）
  5.5. ★★★ 意图判定 → 事件        ← 新增，兜住 3/4/5 漏掉的
  6. 模型答话 / 转人工
```

```python
# 模型侧：只输出意图名，不输出文本、不给参数、不碰钱
INTENTS = ("CONFIRM", "REPRICE", "CANCEL", "PAID", "NONE")

# 代码侧：意图名 → 状态机事件（★ 唯一允许模型影响流程的入口）
INTENT_EVENTS = {"CONFIRM": Event.BUYER_CONFIRM, "PAID": Event.ORDER_PAID}
```

### 2.3 ★★★ 四重闸门（这个设计的全部价值在"它拒绝什么"）

```
① AI 没配 / 没开                → None（退回原行为）
② 该状态下没有任何意图能推进流程  → ★ 不打模型，直接 None
③ 模型判出表外的名字             → None（不猜）
④ ★ 那个事件对该状态【不合法】    → None
   合法性不另写一套，直接查状态机自己的 TRANSITIONS
   ⇒ 模型能影响的只有状态机本来允许的那几个转移
   ⇒ 猜错最多判成 NONE（什么都不发生），不会下错单
   ⇒ 钱的守卫一个都不用动：渠道守卫、报价过期、maxPrice 兜底、下单幂等全在既有代码里
```

**★ 第②条是我第一版漏掉的**：那时每条落到兜底的消息都会多打一次模型，
**哪怕当前在"空闲"状态、根本没有任何意图能推进流程** ——
既费钱又慢，还让"模型调用次数"这个指标失真。
改成先看状态机（`(state, event) in TRANSITIONS`），一个都不合法就别浪费那次调用。
**★ 这不是"关键词库换皮"** —— 它判的是**结构上有没有可能**，
只要某个状态下有合法意图，**全部说法仍然交给模型判**。

### 2.4 ★ 我自己写错的一个 bug（记下来防再犯）

```python
raw = (getattr(reply, "text", "") or "").strip()
#                        ↑ ★ ModelReply 的字段是 .content，不是 .text
```
**后果：每次都取到空串 → `classify_intent` 永远返回 None，而且【不报错】**
（被 `getattr` 的默认值吞了）。表现是"意图层像是没生效"，极难查。
**同仓既有用法都是 `.content`**（`agent.py:1039`、`conversation_ai.py:279`）。

### 2.5 实测

**假模型（打 `_intent_to_event`，不走整条下单链路）：**
```
① 状态驱动短路
   IDLE / PICK_CINEMA / PICK_MOVIE / AWAIT_TICKET / DELIVERED / MANUAL
     → 全部 None，模型调用 0 次  ✓

② 有合法意图的状态
   QUOTED + CONFIRM → buyer.confirm  ✓

③ 拿不准一律不放行
   NONE / REPRICE / CANCEL / UNKNOWN / confrim → 全部 None  ✓

④ 200 字消息 → 不打模型  ✓     ⑤ agent_enabled=False → 完全不判  ✓

⑥ 解析容错（拼错 / 中文 / 两个词 / 空串）→ 全部按预期  ✓
```

**★ 真模型（你配的 deepseek-flash，15 条真实说法）：14/15**
```
  OK  '好的没问题'        → CONFIRM     ★ 以前下不了单的
  OK  '可以，拍我吧'       → CONFIRM     ★
  OK  '要的'             → CONFIRM     ★
  OK  'OK'              → CONFIRM     ★
  OK  '嗯嗯行'            → CONFIRM     ★
  OK  '我已拍下，待付款'     → PAID        ★ 线上抓到的真实原话
  OK  '能便宜点吗' / '太贵了' → REPRICE
  OK  '算了不要了'         → CANCEL
  OK  '什么时候能出票' / '你们家能开发票吗' / '在吗'
      / '我昨天买的那单还能改吗' / '这个影院在哪' → NONE  ← 全部正确没误判
  ★   '正确'             → NONE
```
**「正确」判成 NONE —— 无关紧要**：逐字确认在**第 3 步是最优先的**，
`_is_confirm` 先认它，根本走不到 5.5。**模型路径只是兜底长尾。**

### 2.6 为什么现在只接两个意图

```
CONFIRM  → buyer.confirm   直接影响成单率，且状态机本来就在 QUOTED 认它
PAID     → order.paid      和既有 _looks_like_paid 同一个事件，多一层兜底

REPRICE / CANCEL 【有意不接】：
  它们各自还有"改多少价""退不退得了"这些参数要谈，
  现在手上只有一个名字，接了也只能回一句"转人工"，没有收益。
  ★ 等你的真实会话数据来，按真问题加。
```
