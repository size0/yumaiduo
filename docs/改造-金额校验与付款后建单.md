# 时序改造：金额校验通过 + 已付款，才允许良票建单

> 店主定的铁律（原话）：「**我说清楚，必须金额校验正确，且已付款，才可以良票建单**」
> 日期：2026-10-14

## 一、改之前的时序是错的

```python
# on_buyer_confirm（改之前）
if quote_channel == "WANDA":
    order_id = self._persist_wanda_order(...)   # 只落本地单 ✓ 对
    return out
# 良票：
created = self.api.ch5_create(...)              # ★★★ 付款前就下了上游单
```

**问题：买家刚说「正确」、还没付款，上游单已经下了。这时候：**
```
· 金额不符 / 买家不付 → 上游单撤不掉
  文档 5.5：进入出票中(TICKETING)后【不可拦截】（300008）
  文档 5.7：退票是异步的，而且【可能退不成】
  文档 500001：该订单的供应商【不支持退票】
· 而下单【没有替我们锁座】
  文档全文搜 "lock"：0 处；ch5_preflight 只询价不锁座
  文档原文：「座位状态是秒级变化的，下单成功也不代表出票必然成功」
  ⇒ 早建单没换来任何好处，只换来一张撤不掉的单
```

**★ 而且状态机本来画的就是新时序：**
```
QUOTED + buyer.confirm  → AWAIT_REPRICE（已拍下待改价）
AWAIT_REPRICE + repriced → AWAIT_PAY（改价完成待付款）
AWAIT_PAY + order.paid   → AWAIT_TICKET（待出票）
```
**⇒ 确认 → 拍下 → 改价 → 付款 → 出票。建单不该在付款前。**

## 二、改成了什么

```
① 买家回「正确」
   on_buyer_confirm：
     · 状态 → AWAIT_REPRICE
     · 落一条【本地待付款单】（state=AWAITING_PAYMENT, payment_state=UNPAID）
     · 发 bubble 17（拍下别付款）
     ★ 不调 ch5_create（有断言钉死）

② 卖家在闲鱼改价 → 状态 AWAIT_PAY

③ 买家付款 → 鱼麦多推 order.paid → _from_order_paid
     · ledger.confirm_payment 严格核金额（分文不差）
     · 不符 → 不标已付款 → 不建单
     · 相符 → payment_ok=True

④ on_payment_confirmed（新方法）—— 良票唯一允许建单的地方
     第零道门：状态机允许 order.paid 吗（演练抓到的漏洞，见 §四）
     第一道门：实付金额 == 报价金额
     第二道门：报价张数 == 现在座位数
     全过 → ch5_create → 状态 AWAIT_TICKET + 发 bubble 7
     不过 → AMOUNT_MISMATCH（bubble 23）+ 不建单
```

**★ 关键设计：`ch5_create` 只出现在 `on_payment_confirmed` 里**
（用 AST 查真正的 Call 节点断言，不受注释/字符串干扰 —— 我在这上面踩了三次）

## 四、★★★ 演练抓到一个真漏洞（已修）

```
状态还是【已报价】（买家根本没确认），直接调 on_payment_confirmed
  → 状态机说 (QUOTED, order.paid) 不合法 = False
  → 但它【真的建了单】
```

**原因**：`conv.apply(Event.ORDER_PAID)` 在 `ch5_create` **之后**才执行 ——
它非法时不会拦住前面已经发生的建单。

**修法**：方法开头先问状态机
```python
if (conv.state, Event.ORDER_PAID) not in TRANSITIONS:
    out.ok = False
    out.notes.append("★★★ 付款确认被状态机拦住：… 没有建单")
    return out
```

**★ 为什么这个漏洞值得单独记**：它只在"**状态不对**"这种非 happy-path 上出现，
而 happy-path 演练完全正常。**是我把三条反例也一起跑才发现的。**

## 五、顺带修的两个真问题

### 5.1 `_from_order_paid` 根本不驱动建单

```
改之前：_from_order_paid → ledger.confirm_payment（落库）
                        → 拼一句"已确认付款，这单需要店家处理出票"
        ★ 从来不调 TicketFlow —— 没有 ch5_create 这一步
```
**⇒ 时序一改，良票的单就永远不建了**（买家付了钱，我们什么都没下给上游）。
已改成：付款确认后走 `flow.on_payment_confirmed(...)`，把它的消息转成命令。

### 5.2 找付款对应哪张单时写死了 `provider == "WANDA"`

```python
cands = [... if (r.get("chat_id") == ... and r.get("provider") == "WANDA" ...)]
```
**⇒ 良票的待付款单永远找不到** → 状态落不上、建单也不会发生。
已改成 `in ("WANDA", "LIANGPIAO")`。

## 六、还差一件事（说清楚，没做）

**付款后建单失败怎么办**（座位被抢 200006 / 没供应商 300004 / 价格变了 300006 /
限价不够 300005…）：

```
· 良票侧：文档 order.failed = 「冻结已释放或不曾冻结」
  ⇒ 良票【自动释放全额冻结】，我们不需要有自己的退款能力
· 闲鱼侧：买家已经付给店家了，要【退给买家】
  ★ 但插件端 execute-command.mjs 不认识退款命令类型，
    不认识会掉进 SEND_MESSAGE 兜底分支 → LIVE_CAPABILITY_GATE_REJECTED
    （静默失败，比不写更糟 —— 已特意不那样写）
  ★ 我们后端能发的命令类型只有 4 种，也没有退款
  ⇒ 【当前处理】：need_human=True + note 写明"买家已付款，闲鱼侧要店家退款"
     让人处理，不假装自动化
```

**要做到自动退款，必须先给插件加命令类型（`orders.cancel` + 退款项）。那是插件侧改动。**
