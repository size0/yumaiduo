## 一、★ 最重要的发现：「无法开启」的真因不在那个开关

店主截图里「自动改价开关」是绿的、能点，但他说"无法开启"。
**查下去发现开关本身完全正常，坏的是「保存配置」。**

```
点开关 → 点「保存配置」→ 界面显示 "未保存：配置有问题"
抓 PUT /api/settings 的响应：
  {"ok": false, "problems": ["取票图：没有图片内容"]}
```

### 根因

```javascript
// 前端每次保存都发这个（隐藏输入框的值）：
"ticket_image": {"enabled": "1", "template": ""}
```
```python
# 后端原来是：
if isinstance(_sec, dict) and "template" in _sec:      # ← 只看"有没有这个键"
    _ti_payload = _sec.pop("template")                 # ← 空字符串也被当成图片内容
...
_r = store_upload("取票图", "")   # → {"ok": False, "error": "没有图片内容"}
problems = problems + [f"取票图：{_ti_err}"]           # → problems 非空
if not problems:                                       # → 不落盘
    save_config(data)
```

**⇒ 只要没上传过取票图，功能设置页的「保存配置」就永远失败。**
**⇒ 改任何一个开关都存不进去，而界面只说一句"配置有问题"。**
看起来就是"那个开关有问题"。

### 修法

```python
if isinstance(_sec, dict) and "template" in _sec:
    _raw_ti = _sec.pop("template")
    if isinstance(_raw_ti, str) and _raw_ti.strip():   # ← 只有【真给了内容】才存图
        _ti_payload = _raw_ti
```
**★ 空字符串 = "这次没传新图" = 什么都不做（保留原有图）。**
要删图得走单独的动作 —— **不能拿"没传"当"删除"用**，
那会让"随手保存一下设置"变成"把店主的图删了"。

### 验证

```
本机浏览器：点开关 → 保存 → 「已保存 ✓」、值真的落盘
线上：PUT /api/settings → ok=True, problems=[], ticket_image_error=""
新增回归测试 tests/_check_settings_save.py：7/7
```

## 二、★★ 顺带查出的第二个真问题：布尔被存成字符串

修好保存之后，我注意到存进去的值类型不对：

```
前端开关 = <input type="hidden" value="1">
apply_dict 原来是裸 setattr ⇒ settings.json 里出现 "auto_reprice": "1"（字符串）
```

**为什么危险**（不是洁癖）：

```
bool("1")     = True    ✓ 恰好对
bool("")      = False   ✓ 恰好对
bool("0")     = True    ✗ 一旦哪个开关用 "0" 表示关，就会被【读成开】，而且不报错
```

**修法**：`settings.py` 加 `_coerce_typed`，在 `apply_dict` 里**照字段类型注解**转一次。
```
字符串 "1"     → bool True
字符串 ""      → bool False
字符串 "False" → bool False（不能因为非空就当 True）
数字框 "30"    → int 30
★ 只处理 bool/int/float；枚举值、列表原样返回 ⇒ 现有行为不变
```
**★ 在【入口处】统一转一次，比在几十个读取点各写兼容判断可靠得多。**

新增回归测试 `tests/_check_settings_types.py`：10/10

## 三、「出票及放单」两个开关原来是**静默失效**的

| 控件 | 原来 | 现在 |
|---|---|---|
| **出票方式** 手动/自动 | 代码里**永远自动建单**，根本没读这个配置 | 手动 = 不自动建单，只推状态 + 提示店家去后台出票 |
| **换座状态** 允许/不允许 | `api.ch5_create` 的 payload 里**一直有** `allowSeatChange` 字段，但调用处**从来没传**它 ⇒ 永远走签名默认 `True` | 真按配置传下去 |
| **票速设置** | 早就接了（`_pick_ticket_mode`） | 不变 |

**★ 这两个的失效方式一模一样：不报错，只是"填了没用"。**
第二种尤其隐蔽 —— 参数一直在，只是没人喂给它。

### 手动模式为什么放在"金额门/张数门之后"

```
① 金额门：实付必须等于报价
② 张数门：座位数必须和报价时一致
③ ★ 出票方式=手动 → 推状态 + 提示，直接返回（不建单）
④ 自动 → 调 ch5_create
```
**两道门仍然要过** —— 手动模式也不能拿错价单去人工建单，
只是最后那一步不由我们做。

### 读不到配置时的兜底（两处都是"保持原行为"）

```
出票方式读不到 → 自动（照旧建单）
    ★ 配置坏了不该让所有单都突然不建了 —— 那比"多建一单"严重得多
换座状态读不到 → True（= 签名默认）
    ★ 配置坏了不该让下单直接失败
```

### 验证

`tests/_check_release_mode.py`：**16/16**
```
一、不允许换座 ⇒ /order/create 的 body 里 allowSeatChange=False  ✓
二、手动模式   ⇒ 没有 /order/create，且有明确说明                  ✓
三、切回自动   ⇒ 又建单了，且 allowSeatChange=True                 ✓
四、读不到配置 ⇒ 自动 + 允许换座                                   ✓
```

## 四、「出票溢价」替掉了写死的 3 元

### 先搞清层次（店主问的正是这个）

```
规则命中（有「单张限价」）→ maxPrice = (成本 + 规则的限价) × 张数
没规则命中（兜底）        → maxPrice = 成本合计 + FALLBACK_LIMIT_YUAN × 张数
                                        ↑ domain/quote_rules.py:134 写死 = 3
```

**店主说的"报价规则里有单张限价"是对的，两处是不同层次：**
- 规则里那处管「这条规则加多少钱」
- 兜底那处管「没规则时兜底加多少」← **这就是写死的那个 3**

### 修法

```
「设置 → 出票溢价 → 调整限价 / 溢价上限」
  启用 + 5 元 ⇒ limit = 5/张
  启用 + 0 元 ⇒ limit = 0/张（不加价）
  ★ 未启用    ⇒ limit = 3/张（= 原来的 FALLBACK_LIMIT_YUAN，行为不变）
```

### ★★★ 我第一版写错了，值得记下来

我第一版把"未启用"实现成 **0**。**那会让一部署就把所有没规则命中的
兜底限价从「成本+3/张」收紧到「成本」** —— 等于**拿配置变更悄悄改钱**，
而且方向是"更容易下单失败（300005）"。

**店主说的是"不要硬编码，由这里控制"，不是"把默认值改掉"。**
⇒ 未启用 = 维持现状（3）；启用 = 按配的数（可以是 0，那是店主明确选的）。

**验证**：`_check_fallback_quote.py` 里加了三条：
```
★★ 启用 + 5 元   ⇒ 兜底按 5 元/张
★★ 启用 + 0 元   ⇒ 兜底不加价
★★★ 未启用       ⇒ 仍然是 3（不是 0、也不看 cap_yuan）
```

## 六、★★★ 第三个真 bug：票速设置把值存丢了（而且它真的弄坏了配置）

修完"保存配置"之后，我连续跑测试时发现 `_check_ticket_flow` 的
「档位阈值」断言突然失败：

```
配置=['FAST', 'STANDARD']          ← 只有两档！FLASH 没了
{'FAST': 15, 'STANDARD': 40}       ← speed_flash = false
```

**查下去是个真 bug，而且我在浏览器里点了一次保存就触发了它。**

### 根因：复选框组的形状对不上

```
后端：「票速设置」是【三个独立标量】
        speed_slow / speed_fast / speed_flash
前端：复选框组原来假设【整个组 = 一个数组字段】
        每个 input 都写 data-key = c.key（= "speed_flash"）
        collect() 把它们聚合成数组
⇒ 三个复选框全写进 speed_flash；speed_fast / speed_slow 【根本没有控件】
⇒ 一保存：speed_flash 变成 []（空数组当成 False），
          而 fast/slow 的值再也没人能改
```

### 修法：`keys` 让一个组对应多个字段

```python
# settings.py
speed_flash: bool = field(default=True, metadata=opt(
    label="票速设置", control=C.CHECKS,
    options=["启用慢票（40分钟以上）", "启用快票（15分钟以上）", "启用急速票（1分钟）"],
    keys=["speed_slow", "speed_fast", "speed_flash"],   # ← 新增
    group_label="票速设置"))
```
```
后端序列化：透传 keys + value_by_key（白名单字典，必须显式加）
前端渲染器：按 keys[i] 给每个复选框分配字段名，并打 data-own="1"
前端收集器：按 data-own 分流
              有 data-own ⇒ 写【布尔】到那个字段（各自独立）
              没有        ⇒ 聚合成【数组】（其它页面的老行为不变）
settings._coerce_typed：加一条"list → bool"兼容历史存档
              （空列表 = 没勾 = False；非空 = 勾了 = True）
```

### ★ 数据恢复

**本机和线上都被这个 bug 弄坏过 `speed_flash`（false / []）。**
两处都已恢复成 `true`，现在：
```
线上 speed_tiers() = [('FLASH', 1), ('FAST', 15), ('STANDARD', 40)]
```

### 回归测试

`tests/_check_speed_tiers_ui.py`（本机 15/15，服务器 10/10）
```
① 后端 keys 与字段名对得上、不重复、不漏项
② 序列化透传 keys / value_by_key
③ 前端渲染器读 keys、打 data-own；收集器按 data-own 分流
④ 真浏览器（本机）：三个复选框指向三个【不同】字段；
   勾掉一个 → 保存 → 只有那个字段变，另外两个没被连累
★ 没装 playwright 的环境（服务器）自动跳过第④节，不判失败 ——
  前三节已经把核心判据验了，不为一条测试去改生产环境。
```

## 九、★ 这次最该记住的一条

**店主的症状是「这个开关无法开启」，而真因在【保存】这一步，
不在那个开关。**

排查过程值得复述：
```
① 先验开关本身 → 完全正常（能点、值对、代码真的读它）
② 那就往下游找 → 点"保存配置"
③ 抓 PUT 响应 → problems: ["取票图：没有图片内容"]  ← 真因在这
```
**⇒ "某个控件不好使"的抱怨，先别急着看那个控件 ——
  先确认"改完之后到底存没存进去"。**
一个坏掉的保存会把**所有**控件都变成"不好使"，
而每个控件单独看都是好的。

同理，第二个 bug（类型变成字符串）和第三个（复选框存丢）
都是**只在"保存"这条路上**才暴露的 ——
所以这三个 bug 是在同一轮里被连续挖出来的：
修好第一个，"值真的落盘了吗"这个问题才问得下去。
