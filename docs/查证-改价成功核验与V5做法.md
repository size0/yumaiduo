## 一、★★★ 最重要的结论（它推翻了我的第一版方案）

### V5 判「改价成功」靠的是 **orders.get 回查金额**，不是任何事件

```js
// V5 reprice.mjs:145-147 逐字
const action = await client.orders.changePrice(authorized.order_id,
                {priceFee:authorized.target_amount_fen, transportFee:0});
const after = await client.orders.get(authorized.order_id);
const verified = String(after.orderId) === authorized.order_id &&
                 String(after.accountUnb) === authorized.shop_id &&
                 Number(after.payment) === authorized.target_amount_fen;
return {status:verified?'SUCCEEDED':'VERIFY_FAILED', ...}
```

**★ 连 `changePrice` 的返回值都【明确不信】** —— V5 有专门单测证明：
```js
// test/reprice.test.mjs:140-146
test('a mismatch after the write is still reported as unverified', async () => {
  const client = {...h.client, orders: {...h.client.orders,
                  changePrice: async () => ({ok: true})}};   // 接口说成功
  const result = await executeReprice(...);
  assert.equal(result.status, 'VERIFY_FAILED');              // 回查金额不符 → 仍判未验证
});
```

### 三条否定证据

| 问题 | V5 的答案 |
|---|---|
| 订阅 `order.price.changed`？ | **否。V5 的 subscribes 里没有它** |
| 调 `orders.get` 回查？ | **是，唯一权威判据** |
| 依赖 `changePrice` 返回值？ | **否，明确不信任** |

**`ORDER_REPRICED` / `order.repriced` 在 V5 全项目 0 处存在。**

### ★ 反证：`order.price.changed` 是个「死订阅」

旧版插件（`/opt/wanda-seat-autoquote/current/`）**确实订阅了**它：
```json
"subscribes": ["im.message.received", "order.created", "order.price.changed",
               "order.paid", "order.shipped", "order.finished",
               "order.refund.applied", "order.refund.finished", "order.closed"]
```
但**事件处理器里根本没有这个分支** —— 它的受支持事件集合
（`src/runtime/event-processor.mjs:19-22`）不含 `order.price.changed`：
```js
const ORDER_EVENT_TYPES = new Set([
  'order.created', 'order.updated', 'order.paid', 'order.shipped', 'order.finished',
  'order.closed', 'order.refund.applied', 'order.refund.finished',
]);
```
**⇒ 订阅了却没人处理。V5 直接把这个订阅删了。**
这是既有工程判断：**别拿事件当改价成功信号。**

### 真正的成功信号载体 = 命令结果回传

```
插件 claim 命令 → authorize → changePrice → orders.get 回查
  → POST /api/v1/commands/{id}/result   ← 信号从这里回来
  → 后端 record_result → reprice_result_notice
  → 状态 'REPRICE_SUCCEEDED' → bubble 18
```
V5 的触发契约（模板矩阵逐字）：
```python
contract('REPRICE_SUCCEEDED', '改价', 'Command/Plugin', '改价结果明确成功',
         'REPRICE_SUCCEEDED', (18,31,22,33), next_actions=('核对后付款',))
```
**来源标注是 `Command/Plugin`，不是 Event。** `(18,31,22,33)` 就是 bubble 编号。

后端还会**独立再验一遍**（`store.py:352-353`）：
```python
if kind=='CHANGE_ORDER_PRICE' and data['status']=='SUCCEEDED' and (
        type(data.get('price_after_fen')) is not int
        or data['price_after_fen']!=current.get('target_amount_fen')):
    raise ValueError('REPRICE_RESULT_AMOUNT_MISMATCH')
```

## 三、根因：改价命令**永远不会生成**（先有鸡还是先有蛋）

### 证据

```python
# application/plugin_runtime.py:221  —— 命令只在 side=="REPRICE" 时生成
if side == "REPRICE":
    commands.append(Command(type="CHANGE_ORDER_PRICE", ...))

# domain/conversation.py  —— side 来自这张表
SIDE_EFFECTS = {Event.ORDER_REPRICED: "REPRICE",        # 调改价接口
                Event.ORDER_PAID: "TICKET_OUT",
                Event.TICKET_FAIL: "REFUND",
                Event.QUOTE_REISSUED: "REPRICE_AGAIN"}

# application/ticket_flow.py:1335 on_buyer_confirm
推的是 BUYER_CONFIRM  ← 不是 ORDER_REPRICED
```

**⇒ 循环依赖**：
```
要生成"去改价"的命令，必须先有 ORDER_REPRICED（改价成功）；
而改价成功又必须先有那条命令。
⇒ 命令一次都生不出来 ⇒ 插件领不到 ⇒ changePrice 永远不会被调
⇒ 买家收到「我改价后您再付款」→ 等着 → 价格从没变过。
```

**这就是 V5 说的「优先修『没人调改价接口』」的那个问题。**

### 正确做法（照 V5）

```
买家拍下（on_buyer_confirm）
  → 落本地待付款单
  → ★ 直接生成 CHANGE_ORDER_PRICE 命令
       target_amount_fen = quote.total_price_fen
       transportFee = 0（插件固定传 0）
  → 发 bubble 17（拍下别付款）
插件每秒 claim → 领到改价命令
  → orders.get（回查#1，拿改价前的快照）
  → POST /authorize-execution（后端核订单状态 + 回 target_amount_fen）
  → orders.changePrice(order_id, {priceFee:目标价, transportFee:0})
  → orders.get（回查#2）→ 核 payment == 目标价 → SUCCEEDED / VERIFY_FAILED
  → POST /commands/{id}/result
后端 record_result
  → 状态 SUCCEEDED → 推 ORDER_REPRICED → 状态机 → AWAIT_PAY + bubble 18
  → 状态 VERIFY_FAILED / FAILED → 不许对买家说"改价成功"，转人工
```

**★ 关键修正**：`CHANGE_ORDER_PRICE` 的生成点要从
「`ORDER_REPRICED` 的 side_effect」搬到「`on_buyer_confirm` 的返回路径」。

## 四、★ 另一个可借鉴的坑：重试前必须先回查

V5 的注释（逐字）：
```js
// CHANGE_ORDER_PRICE carries no idempotency key (the developer guide's endpoint
// table requires one only for red-flower and remind-receipt), so an unconfirmed
// write must never be retried blindly. What is safe is to LOOK: if the order
// already holds the authorised amount, the write landed and only its response was
// lost, which is a success rather than an unknown.
```

**⇒ 改价接口没有幂等键。重试前必须先 `orders.get` 回查金额；
如果金额已经是目标价，说明上次其实成功了（只是响应丢了），
这时【不能再改一次】。** 盲目重试可能重复扣款。

V5 的三态分类（重试策略完全不同）：
```js
const refusals = new Set(['CANNOT_MODIFY_FEE','ORDER_CLOSED','ORDER_NOT_FOUND',
  'ORDER_ALREADY_PAID','INVALID_PARAM','INVALID_PARAMS','PERMISSION_DENIED','FORBIDDEN']);
const transientCodes = new Set(['E_PLUGIN_RATE_LIMITED','E_IM_WS_UNAVAILABLE']);
// refused → 不重试；transient → 最多 2 次（每次重试前先回查）；unknown → 不重试
```
