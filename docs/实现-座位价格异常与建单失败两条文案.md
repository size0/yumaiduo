## 二、★★★ 问题 1：找到了 —— 判据解析了却从来没人读

### 店主说这是「识别座位价格异常」→ 那异常就是识别返回里的 `priceMismatch`

```

**良票文档 2210 行原文：**
```
priceMismatch=true 通常意味着【漏识别了座位】，建议人工复核。
```

### ★★★ 缺口的真相

```

```

**⇒ 「识别座位价格异常」这个信号我们收得到、存下来了，但没人用它做任何事。
所以 bubble 44 的文案挂在模板里、永远发不出去。**

### 已修

```
application/ticket_flow.py  _after_recognition 最前面加一道判：
    if result.price_mismatch:
        → 推 RECOGNIZE_FAIL（状态回 IDLE，买家重发即可）
        → 发 RECOG_FAIL 的 seat_price_abnormal 变体（文案 = bubble 44 原文）
        → 【不进询价/下单】—— 座位都没认全，询价没意义
        → note 里带上 seatConfirmReasons 方便排查

templates.py  RECOG_FAIL 新增变体：

    ★ 与 bubble 44 逐字一致；与 seat_blocked 文案相同但**分开命名** ——
      排查时一眼看出是"价格对不上"还是"座位被遮挡"。

**★ 为什么放在最前面判**：它是**识别层面**的问题。座位没认全 →
后面询价拿到的价与买家看到的对不上 → 下单必错。同业也把它单列一个状态。

**⇒ 这张图建单成功，没能复现"创建订单失败"。**

★ 顺带确认一个事实（座位图实测）：
```
areaId=0    原价 3000 分
areaId=4909 原价 3000 分     ← 两个分区原价【相同】
两个座位 seatPriceFen 都是 2990、status 都 AVAILABLE

```
**⇒ 座位图显示同价，上游按分区算的实际价不同。** 这就是这类场景的本质。

### 即便如此，bubble 8 也该接上（模板在、没人调）

```
改前：on_payment_confirmed 建单被拒一律发 RECOG_FAIL + fail_reason
改后：200006 / 200007 / 300005 → CREATE_FAILED（bubble 8 原文）
      300004 / 300006 / 300010 / 其它 → 保持 RECOG_FAIL（通用）
```

**为什么这样分（判据写进代码注释了）：**
```
bubble 8 的处置方式【不一样】：
  通用那条 = "重新发截图"
  bubble 8 = "【取消后分别重新截图】下单"
             —— 一张单里混了价格/状态不一致的座位，只能拆开重下
说错了买家会反复重发同一张图，永远下不成。

· 200006 座位已售   → 座位本身有问题
· 200007 选座违规   → 座位本身有问题
· 300005 实际价超限价 → 我们给的价与这批座位的实付对不上
                        （正是"位置价格不对"的字面意思）
· 300004 无供应商 / 300006 票价变动 / 300010 重复单
  → 不是"座位价格不对"，套 bubble 8 会误导买家去拆单
```

**★★ 这里我要标明一个不确定：** 店主给的对照表把 bubble 8 的场景标签写作
「**待出票后**，建单失败」，而上面那个 demo 序列里 bubble 8 前面是
`7 待出票` + `trade-seller 我已修改价格` —— 也就是说它可能出现在
**付款前**（本地已建单、上游还没建）的阶段。

我把 200006/200007/300005 映射到 bubble 8 是**按文案语义推断**的。
**如果实际触发信号不是这三个码，请店主告诉我那条真实日志里的 failCode。**
