## 二、做了什么

### 1. 新模块 `application/ticket_image.py`

管一张图的完整生命周期：
```
store_upload(name, base64)   存店主的图（校验 → 落盘）
ensure_uploaded(ident, secret)  没缓存过 URL 就先上传一次
image_for_send(cfg)          出票时要用的 {imageUrl,width,height}，没有就 None
mark_uploaded(url, w, h)     记下上传结果
```

**四个不猜的取舍**：

| 取舍 | 做法 | 理由 |
|---|---|---|
| 认图片类型 | **按魔数**，不看扩展名 | 扩展名可以随便改，魔数不会 |
| 上传时机 | **第一次要用时上传**，URL 缓存进文件 | 平台不让凭空造 URL；每发一次传一次是浪费，还可能触发频率限制 |
| 换图 | **清掉旧 URL** | 否则会发出上一张图（真会发生的 bug） |
| 校验位置 | **后端也校验一遍** | 界面校验只是提示，后端才是防线 |

### 2. 出票成功后附一张

```
位置：ticket_flow._on_success（Event.TICKET_OK 之后）
做法：排一条 SEND_MESSAGE + image，带 dedupe_key=ticket_image:<单号>
     ⇒ 同一单只发一次（幂等）
```

**★ 三条"不让它拖垮主流程"的设计**：
```
① 默认 enabled=False / 没配图 ⇒ image_for_send() 返回 None ⇒ 什么都不做
   （默认行为一个字不变）
② 上传失败 ⇒ 返回 None 不发图，但【不抛异常】
③ 出票点用 try/except 包住，失败只记一句 note：
   "★ 取票图排队失败（不影响出票）"
   —— 票码才是买家真正要的，图是附赠的
```

## 三、★ 修一个警告，引入一个更严重的问题（然后修回来）

**经过**：
```
架构审计报「孤儿模块 application.ticket_image」← 因为我在函数内动态 import
⇒ 我改成模块级 import 来消掉这个警告
⇒ 结果引入了【循环依赖】：
     plugin_api → plugin_runtime → service → ticket_flow
       → ticket_image → plugin_api      ← 闭环
   （ticket_image 为了取 plugin_secret 而 import plugin_api）
```

**★ 修一个警告，引入一个更严重的问题。** 而且**全量自检还报"全部通过"** ——
我是单独跑架构审计才看见的（循环依赖那条在别的套里）。

**⇒ 正确修法**：`ticket_image` 只做"图的生命周期"，
**取密钥是调用方的事** ⇒ `ensure_uploaded` 收 `secret` 参数，
`ticket_flow` 自己取密钥传进来。这样 `ticket_image` 不 import 任何
`application` 模块，环就断了，而且**不需要动态 import**。

**结果**：`application.ticket_image ← application.ticket_flow ✓`

## 四、★ 另一个我自己造的问题

**插入模块级 import 时，我插进了跨行 import 的中间**：
```python
from integrations.liangpiao.api import (MATCH_EXACT, PRICE_LIMIT,   ← 括号没结束
# ★ 2026-10-14：模块级 import ——        ← 我插在这里
from application import ticket_image                          ← 插在括号里
                                        QuoteParams, RecognitionResult,  ← 续行
```
**直接语法错误。**

**根因**：我按"第一个不以 import/from 开头的行"找插入点 ——
而**跨行 import 的续行也不以 import 开头**。
**又一次"用行规律猜结构"栽了**（前面注册表也是这个问题）。

**⇒ 修法**：找插入点必须**按括号配平**（`depth += l.count("(") - l.count(")")`），
不能按行首关键字。
