# 给负责出票系统的 AI：加一个「影院 ID 映射」只读接口

> 提出方：ticket-agent（插件侧）
> 目的：让插件能把「良票识别到的影院」映射到「万达影院 ID」，从而走万达渠道报价。
> 日期：2026-10-13

---

## 一、为什么需要这个接口（背景）

插件侧现在这条链路是通的：

```
买家发图 → 良票识别 → 拿到 cityCode + cinemaId（良票侧）
                       ↓
              ★ 需要在这里做一次映射
                       ↓
              万达 city_id + cinema_id
                       ↓
        用万达影院 ID 取场次 → 桥 /api/showtime/seats 取会员价
```

**映射表已经存在，而且是人工维护好的**：

```
文件：/var/lib/ticket-system-v5/cinema-identity.sqlite3   ← V5 那边的库
表：  cinema_identity_mapping        843 条
```

```sql
CREATE TABLE cinema_identity_mapping (
    source_provider TEXT NOT NULL CHECK(source_provider='LIANGPIAO'),
    source_city_id   TEXT NOT NULL,
    source_cinema_id TEXT NOT NULL,
    target_provider TEXT NOT NULL CHECK(target_provider='WANDA'),
    target_city_id   TEXT NOT NULL,
    target_cinema_id TEXT NOT NULL,
    PRIMARY KEY(source_provider, source_city_id, source_cinema_id),
    UNIQUE(target_provider, target_city_id, target_cinema_id),
    ...
);
```

**样例数据**：

| source_city_id | source_cinema_id | target_city_id | target_cinema_id |
|---|---|---|---|
| 350900 | 7261 | 80 | 379 |
| 110100 | 42   | 290 | 595 |

**已验证的完整链**（插件侧实测，只读、不建单）：

```
良票识别       cityCode=350900  cinemaId=7261  「万达影城（宁德万达广场激光IMAX店）」
查映射表        → 万达 city=80  cinema=379  「宁德万达广场店」
万达场次        cinemaId=379 → 166 场
桥取座位图      W+专享 会员价 50.26 元  ← 成本
规则引擎        每张 +1 元，取整到角 → 售价 51.26 元
```

★ 注意：**两套名字完全不同，按名字匹配实测只有 35.9% 命中率。
必须按 ID 映射** —— 这就是为什么需要这个接口。

## 二、★ 前提问题：出票系统现在读不到这张表

我实测过（在服务器上）：

```
$ sudo ls -la /var/lib/ticket-system-v5/cinema-identity.sqlite3
-rw-rw---- 1 ubuntu ubuntu 5038080 Oct 10 10:13 ...

$ sudo ps -o user -p <8000端口进程>
ticket-+  （即 ticket-system 用户）

$ sudo -u ticket-system test -r /var/lib/ticket-system-v5/cinema-identity.sqlite3
→ ★ 不可读
```

**原因**：该文件与目录都属 `ubuntu:ubuntu`，权限 `rw-rw----`，
而 8000 端口的后端以 **`ticket-system`** 用户运行。

**所以第一步要解决读权限。** 见下节两个方案，请选一个。

---

## 三、两个实现方案（选一个）

### 方案 1：直接读原库（授权）

给 `ticket-system` 用户加读权限。两种做法：

```bash
# 1a) 把 ticket-system 加入 ubuntu 组（然后必须重启后端进程才生效）
sudo usermod -aG ubuntu ticket-system
sudo systemctl restart <8000那个服务>

# 1b) 或用 ACL（不用改组）
sudo setfacl -m u:ticket-system:rx /var/lib/ticket-system-v5
sudo setfacl -m u:ticket-system:r  /var/lib/ticket-system-v5/cinema-identity.sqlite3
```

★ 注意两点：
- **SQLite 只读打开要用 `?mode=ro`**，否则会在同目录尝试建 `-wal`/`-shm`
  （那目录 ticket-system 写不了，会报错）：
  ```python
  sqlite3.connect("file:/var/lib/ticket-system-v5/cinema-identity.sqlite3?mode=ro",
                  uri=True)
  ```
- 这是 **V5 的库**，出票系统只许读、绝不许写。

### 方案 2：定期复制到出票系统自己的数据目录（★ 我更推荐）

```bash
# 复制到出票系统自己的目录（它已经有 cinema_cache.sqlite 在那里）
sudo cp /var/lib/ticket-system-v5/cinema-identity.sqlite3 \
        /var/lib/ticket-system/backend-data/cinema-identity.sqlite3
sudo chown ticket-system:ticket-system \
        /var/lib/ticket-system/backend-data/cinema-identity.sqlite3
sudo chmod 640 /var/lib/ticket-system/backend-data/cinema-identity.sqlite3
```

然后加一个定时刷新（比如每 10 分钟，或每天一次）：

```bash
# /etc/cron.d/cinema-identity-sync  或 systemd timer
*/10 * * * * root cp /var/lib/ticket-system-v5/cinema-identity.sqlite3 /var/lib/ticket-system/backend-data/cinema-identity.sqlite3.tmp && mv /var/lib/ticket-system/backend-data/cinema-identity.sqlite3.tmp /var/lib/ticket-system/backend-data/cinema-identity.sqlite3 && chown ticket-system:ticket-system /var/lib/ticket-system/backend-data/cinema-identity.sqlite3
```

**为什么我更推荐方案 2**：
- 不动 V5 的权限（V5 是生产系统，权限收紧是有意的）
- 出票系统自己的数据都在 `backend-data/`，一致
- 用 `mv` 原子替换，读到的一半旧半新文件不会发生
- 已经有先例：`cinema_cache.sqlite` 就是这么维护的

★ 方案 2 的代价：**最多滞后一个刷新周期**。
如果你手动维护完想立刻生效，可以在维护脚本里顺手触发一次同步。

## 四、接口契约

### 4.1 路径与方法

```
GET /api/cinema/wanda-lookup
```

**必须加入 `X-Plugin-Bridge-Key` 的免会话白名单**
（就是现在 8000 端口上那份，`main.py` 里那个精确路径白名单，
和 `/api/auth/internal/wplus-accounts`、`/api/showtime/seats` 放一起）。

### 4.2 请求参数

| 参数 | 必填 | 说明 |
|---|---|---|
| `cityId` | ✅ | 良票侧 cityCode（如 `350900`） |
| `cinemaId` | ✅ | 良票侧影院 ID（如 `7261`），**是良票的，不是万达的** |

```
GET /api/cinema/wanda-lookup?cityId=350900&cinemaId=7261
```

### 4.3 响应

**查询成功（有映射）—— HTTP 200：**

```json
{
  "code": 0,
  "data": {
    "bizCode": 0,
    "bizMsg": "",
    "mapped": true,
    "wandaCityId": "80",
    "wandaCinemaId": "379",
    "wandaCinemaName": "宁德万达广场店",
    "sourceCinemaName": "万达影城（宁德万达广场激光IMAX店）"
  }
}
```

**查不到映射（★ 这是【正常情况】，不是错误）—— HTTP 200：**

```json
{
  "code": 0,
  "data": {
    "bizCode": 0,
    "bizMsg": "",
    "mapped": false,
    "reason": "NO_MAPPING"
  }
}
```

★ **`mapped: false` 必须返回 200 而不是 404**。
因为"这家影院没有万达映射"意味着**这单走良票渠道**，是正常业务分支，
不是接口错误。如果返回 404，插件侧会把"该走良票"误当成"接口坏了"。

**映射表不可读 / 库不存在：**

```json
{
  "code": 0,
  "data": {
    "bizCode": 0,
    "bizMsg": "",
    "mapped": false,
    "reason": "IDENTITY_STORE_UNAVAILABLE"
  }
}
```

★ 这种情况**也要能区分出来**（`reason` 字段）。
否则"表坏了"和"这家没映射"会混成同一个结果 ——
前者会让所有万达单静默退化成良票单，且**没有告警**。

**参数缺失 —— HTTP 400：**

```json
{"detail": "cityId 和 cinemaId 必填"}
```

### 4.4 参考 SQL

```sql
-- 主查询
SELECT target_city_id, target_cinema_id
FROM cinema_identity_mapping
WHERE source_provider = 'LIANGPIAO'
  AND source_city_id   = :cityId
  AND source_cinema_id = :cinemaId;

-- 顺带取个名字（给日志/排查用，可选）
SELECT canonical_cinema
FROM cinema_identity
WHERE provider = 'WANDA' AND provider_cinema_id = :wandaCinemaId;
```

### 4.5 实现要求

1. **只读**：`?mode=ro` 打开，不建表、不写、不迁移。
2. **连不上不要抛 500 给插件**：按 4.3 的 `IDENTITY_STORE_UNAVAILABLE` 返回 200。
   （插件侧会把它当"映射不可用"处理，而不是网络错误重试）
3. **每次都读库、不要长期缓存到内存**：
   这张表是人工维护的，维护后希望尽快生效。
   如果要缓存，TTL 不超过 60 秒。
4. **别把整张表返回给插件**：只要单条查询结果。
