# 检查报告：候选买家是怎么选择的（发现 3 个真缺陷，已修）

> 起因：店主说「检查一下候选买家是怎么选择的」
> 对象：`on_candidate_pick` / `_ask_candidate` / 状态机的 `PICK_* ↔ QUOTED`
> 日期：2026-10-13

---

## 〇、结论

```
设计本身是对的：
  · 只对【尚未唯一的维度】发问（cinemaId 有了就不再问影院）
  · 走二次确认接口（不重调模型、不计费）
  · 序号不对不报错，直接重发候选
  · 记下 recognizeId，买家回复时接着用

★★★ 但状态机的三条边缺失 + 一个事件从来没被推 —— 多轮消歧根本走不完：
  每多问一轮就「非法兜底 → 转人工」，而且兜底不改状态，会话卡死。
```

---

## 一、正常设计（这部分是对的）

```
买家发截图
   ↓
识别回来 matchLevel=CANDIDATE
   ↓
_ask_candidate：
   · pending_dimensions() 算出还差哪些维度
   · 只问 pending[0]（第一个没收敛的）
   · 推 RECOGNIZE_MULTI_* → 进 PICK_CINEMA/PICK_MOVIE/PICK_SHOW
   · 把候选存到 conv.last_candidates（三个维度都存）
   · 发 DISAMBIG（bubble 40），文案 = 只含被问的那个维度
   ↓
买家回「影院2」
   ↓
on_candidate_pick：
   · _parse_pick 解析出 (kind, index)
   · 从 conv.last_candidates[kind] 取出选中的 ID
   · 调 ch7_confirm（★ 不重调模型、不计费）
   · 收敛了就往下报价，没收敛就接着问下一个维度
```

**★ 判据：`pending_dimensions()` 只看 ID 有没有值** —— 文档要求「cinemaId 已有值就不要再拿 candidates.cinemas 去问」，这条我们做对了。

## 二、★★★ 缺陷 1：`on_candidate_pick` 从来没推 `BUYER_PICK`

**现场：**

```python
# on_candidate_pick 里唯一的 conv.apply：
conv.apply(Event.RECOGNIZE_FAIL)      # 只在"识别句柄过期"那一条分支
# ★ 买家选定候选之后，什么都不推 —— conv.state 停在 PICK_*
```

**后果链：**

```
conv.state == PICK_CINEMA（没变）
   ↓ 接着 _after_recognition 去推 RECOGNIZE_MULTI_MOVIE
   ↓ 而 (PICK_CINEMA, RECOGNIZE_MULTI_MOVIE) 在表里【没有】
   ↓ 走非法兜底：
       note='未预料的事件：待确认影院 收到 recog.multi.movie，转人工'
       needs_manual=True
   ★ 而且非法兜底【return 时不改 self.state】——
     会话永远卡在 PICK_CINEMA 上
```

**证据：** 三条 `(PICK_*, BUYER_PICK) → QUOTED` 的转移**本来就在表里**，
`REPLY_OF` 还给它配了 `QUOTE_CARD` —— 说明原设计就是要推这个事件，只是漏了调用。

**修法：** 加 `_apply_pick_event()`，在确认成功后推 `BUYER_PICK`。
★ 只取「状态推进」这个副作用，**忽略它的 `reply_key="QUOTE_CARD"`** ——
这时还没收敛到唯一场次，发报价卡是错的；真正该发什么由 `_after_recognition` 决定。

## 三、★★★ 缺陷 2：状态机缺 `(QUOTED, RECOGNIZE_MULTI_*)`

`_ask_candidate` 有两个来源状态：

```
① RECOGNIZING —— 识别刚回来           → 表里有 ✓
② QUOTED      —— ★ 买家选完上一轮之后  → 表里【没有】✗
```

**修法：** 补三条

```python
(ConvState.QUOTED, Event.RECOGNIZE_MULTI_CINEMA): ConvState.PICK_CINEMA,
(ConvState.QUOTED, Event.RECOGNIZE_MULTI_MOVIE): ConvState.PICK_MOVIE,
(ConvState.QUOTED, Event.RECOGNIZE_MULTI_SHOW): ConvState.PICK_SHOW,
```

**⇒ 不补这条：买家答完第一轮，第二轮就转人工 —— 多维度消歧走不完。**

---

## 四、★★★ 缺陷 3：状态机缺 `(QUOTED, RECOGNIZE_OK)`

买家答完**最后一个**待确认维度时，二次确认收敛成 `EXACT`，
`_after_recognition` 推的是 `RECOGNIZE_OK` —— 而它原来**只从 `RECOGNIZING` 出发**。

```
⇒ 最后一轮必然走非法兜底转人工 —— 消歧永远收不了尾。
   （表现：三轮都答对了，最后却"转人工"）
```

**修法：** 补两条（`RECOGNIZE_FAIL` 一并补，最后一轮确认失败要能正常报错而不是转人工）

```python
(ConvState.QUOTED, Event.RECOGNIZE_OK): ConvState.QUOTED,
(ConvState.QUOTED, Event.RECOGNIZE_FAIL): ConvState.IDLE,
```

## 五、★★ 缺陷 4：跨维度回答会被受理

**现场：**

```
我们问【影院】→ 买家看到【影院1】甲影城 / 【影院2】乙影城
买家回「影片1」（这个词他根本没看到过）
→ ★ 系统真的拿 movieId=201 去二次确认了
→ 而且发出去的消息里【选项列表还是影院】← 消息和实际动作脱节
```

**原因：** `conv.last_candidates` 里三个维度的候选**都在**（识别时一次性下发），
所以按 `kind` 取 `movies` 也能取到 —— 但那个影片列表**买家从来没见过**。

**修法：** 只认【正在问的那个维度】

```python
asked = {
    ConvState.PICK_CINEMA: "cinema",
    ConvState.PICK_MOVIE: "movie",
    ConvState.PICK_SHOW: "show",
}.get(conv.state)
if asked is not None and kind != asked:
    → 重发【当前在问的那一份】候选，不消耗、不报错、状态不乱走
```

**★ 判据用 `conv.state`** —— 它就是"我们最后问了哪个维度"的权威来源，
不用另存一个字段（另存会多一处可能不同步的状态）。

## 六、★★★ 店主的第二项要求：候选只回数字

> 「并且修改一下 回复1-2-3-4就行 前面影院去掉」

### 6.1 列表格式：去掉前缀

```
改前：  【影院1】甲影城（天津）
        【影院2】乙影城（天津）
        直接回复对应指令即可完成确认（例如：影院1）

改后：  1. 甲影城（天津）
        2. 乙影城（天津）
        直接回复上面的数字即可完成确认
```

**★ 为什么可以去掉前缀：** 每次只问**一个**维度（见 `_ask_candidate`），
消息本身已经限定了是哪一类 —— 再加前缀只是让买家多打字。

### 6.2 回复解析：纯数字也认

```python
def _parse_pick(raw):
    # 「影院1」→ ("cinema", 1)   带前缀，兼容老买家习惯
    # 「1」    → (None, 1)       ★ 纯数字，维度未知
    ...
```

**★★ 为什么纯数字的维度【不在 _parse_pick 里定】：**

```
service.py 的路由判据是 index > 0 ——
如果 _parse_pick('1') 返回了 'cinema'，那买家在【任何状态】下发"1"
都会被当成选座，把普通聊天误判成选座流程。
只有 on_candidate_pick 才知道"我们正在问哪个维度"，
所以纯数字只在【那里】被按 conv.state 补上维度。
```

### 6.3 ★★ 踩出来的回归：候选路由吃掉了 FAQ 关键词

**改完立刻被 `_check_service` 抓到：**

```
qa 表里的纯数字关键词：999 / 001 / 002 / 003 / 004 / 005 / 111
而我们的文案对买家承诺了「常见问题回复999」

⇒ 候选路由先吃掉它们 → 买家按文案发 999，收到的是
  「上次识别已过期」/「重发候选」，拿不到常见问题
```

**修法：已登记的关键词优先**

```python
is_known_keyword = bool(text) and qa_module.reply(text) is not None
if (index > 0 and not is_known_keyword
        and s.last_question in ("screenshot", "pick")):
    → 走候选
```

**★ 原则：兑现给买家的指令，优先级高于内部流程判断。**
文案里写了"回复999"，那 999 就必须永远能拿到常见问题。

### 6.4 实测

```
① 三轮消歧全用纯数字
   第2轮 回「1」→ PICK_MOVIE  需人工=False   confirm{cinemaId:101}
   第3轮 回「1」→ PICK_SHOW   需人工=False   confirm{movieId:201}
   第4轮 回「1」→ QUOTED      需人工=False   confirm{showId:s1}

② 带前缀的老写法仍然可用（向后兼容，老买家不会报错）
   回「影院2」/「影片1」/「场次1」→ 同样正常推进

③ 跨维度回答仍然被拦（重发当前在问的那份候选）
```

## 七、多轮消歧实测（修复前后对比）

```
① 三轮消歧（影院 → 影片 → 场次）
   第1轮 → PICK_CINEMA 问影院
   第2轮 回影院2 → PICK_MOVIE  需人工=False ✓   confirm{cinemaId:102}
   第3轮 回影片1 → PICK_SHOW   需人工=False ✓   confirm{movieId:201}
   第4轮 回场次1 → QUOTED      需人工=False ✓   confirm{showId:s1}
   ★ 修复前：第2/3/4 轮全部转人工

② 我们问影院、买家回「影片1」→ 重发影院候选，不调 confirm ✓
③ 序号越界（影院99）→ 重发候选，不调 confirm ✓
```

## 七、加了 11 条断言锁住这四个缺陷

```
★★ 选完影院 → 推进到问影片（不许转人工）
★★ 选完影片 → 推进到问场次
★★★ 答完最后一个维度 → 收敛（不许转人工）
★★★ 收敛后的确没打人工标记
★★ 跨维度回答 → 不调二次确认
★★ 跨维度回答 → 状态停在原维度（不乱走）
★  跨维度回答 → 重发【当前在问的那份】候选
★  跨维度回答 → 不消耗、不报错
```

**★ 判据不是"没报错"，是【状态真的往前走了 + 没打人工标记】**
—— 因为非法兜底**也只返回 DISAMBIG**，光看文案看不出坏。
这是这组 bug 能藏这么久的原因。

## 八、★ 为什么这组 bug 之前没被测出来

```
现有测试七、只断言了【单维度】消歧：
  CANDIDATE_RESULT 里 candidates.cinemas = [] / movies = []
  ⇒ 只测了 PICK_SHOW 这一个分支，而且只测了第 1 轮
  ⇒ 缺陷 2/3（第二轮、最后一轮转人工）根本没机会暴露
  ⇒ 缺陷 1（不推 BUYER_PICK）在单轮场景下也不暴露
     （第 1 轮的状态是 RECOGNIZING，RECOGNIZE_MULTI_SHOW 从它有定义）

教训：消歧测试要覆盖【多轮】和【多维度】，单轮单维度测不出状态机缺边。
```

## 十、★★★ 顺带查出的另一个坑：存盘快照会盖住代码改动

**现象：** 改完 templates.py、重启服务，/api/templates 返回的还是旧文案。

**原因：**

`
application/store.load_template_overrides() 的规则是
   「data/templates.json 里有 → 覆盖代码里的」
这是为了【让运营改的文案活下来】，本身是对的。

但代码里改了【默认文案】时，存盘那份旧快照会把它盖回去 ——
表现为：改了代码、重启了服务，界面上和发出去的还是旧的。
★ 我当时就被这个骗了一轮，以为服务没重启好。
`

**核对后确认没有运营改动会丢：**

`
存盘 32 条 vs 代码 33 条
  · 31 条逐字一致
  · 只有 DISAMBIG 一条不同 ← 就是我刚改的那条
  · 代码多一条 TICKET_MODE_CHANGED（新加、已停用的 bubble 33）
⇒ 这份存盘是一份和代码同步过的快照，不是运营手改的成果
`

**处理：删掉 data/templates.json**（已备份到 %TEMP%\templates.json.bak）
`
删掉之后：代码里的模板成为权威，界面上一保存就会重新生成这份文件。
`

**★ 加了哨兵防止再被坑（_check_channel.py）：**
`
· 没有存盘快照 → 报告「代码就是权威」（最干净的状态）
· 有存盘快照   → 【把差异量出来】并打印，让人一眼看到「存盘正在盖住代码」
  ★ 不报错 —— 运营本来就该能改文案，有差异不一定是问题；
    关键是【看得见】。
· 有渠道覆盖/变体的模板，存盘里也得有对应字段 ——
  否则界面上看起来「没保存/没生效」
`
