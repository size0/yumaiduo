# 万达出票 · 发货链路

> 这份文档描述的是**出票工作台 → 买家收到取票图**的完整链路。
> 每一步都标了代码位置，方便对照排查。
>
> ★ 来源：由出票工作台那边提供，本仓库据此核对了自己的实现。
>   核对结果见文末「与本仓库实现的差异」。

---

## 链路（当前实际状态，含代码位置）

```
① 待出票订单「去出票」
     WandaAiPlugin.tsx:373 → App.tsx:228 openWandaOrderForIssuing()
     → setPage('workbench')，并把该订单作为 wandaOrderBinding 交给工作台

② 出票工作台：选影院 → 场次 → 座位 → 锁座下单 → 支付

③ 支付成功那一刻（Workbench.tsx:2280）
     rememberWandaIssuance(binding, 本地订单号)
     → 把「本地订单号 → {万达订单号 orderId, shop_id}」写进 sessionStorage
       （注意：这是自动交割能成立的前提，存的是浏览器 sessionStorage）

④ 取票码回来
     fetchPaidTicketCode()   自动触发：券支付路径 Workbench.tsx:3037 / 3049
                             也可人工点按钮「继续出票」（Workbench.tsx:5314 / 5959）
     → 后端 /api/order/ticket-code 取万达取票码
     → 写入本地订单 _ticket_cache（影院/地址/影厅/座位/场次/结束时间/取票码/二维码）
     → 成功后立刻调 ⑤

⑤ 自动交割 submitBoundWandaFulfillment（Workbench.tsx:2339）
     a. readWandaIssuance(本地订单号) → 读不到绑定直接 return（不发）
     b. 幂等：同订单 + 同二维码内容 → return
     c. 查 V5 订单详情：已有 ticket_delivery → 跳过，提示「原订单已有交付记录」
     d. 生成要发的图（三级降级）：
          ① drawTicketTemplateDataUrl(...)  ← 出票工作台那套 canvas 渲染（和操作员看到的图一致）
          ② /api/order/ticket-image-by-code?code=… ← 后端渲染兜底
          ③ buildWandaQrImage(...)          ← 纯二维码兜底
     e. POST /api/wanda-orders/{orderId}/ticket-image?shopId=…  {data: base64}
          → 返回 image{imageUrl, width, height}
     f. POST /api/wanda-orders/{orderId}/tickets?shopId=…
          { image, source:'AUTO', provider_order_id, submission_id:'wanda-{orderId}' }

⑥ 后端转发 backend/app/routes/wanda_orders.py
     ticket_handoff() → _write_v5('/{order_id}/{action}', 投递密钥, {shop_id}, body, operator)
     → 打给 V5 的写接口（带 X-Operator-Id）

⑦ V5 侧（/opt/ticket-system-v5）
     wanda_delivery.submit() → 建 DELIVER_TICKET 命令：
        delivery_provider = 'WANDA'，delivery_source = body.source，
        image = {imageUrl, width, height}
     硬校验（wanda_delivery.py:70-74）：image 的键必须**正好**是 {imageUrl,width,height}，
        且 imageUrl 必须是 **alicdn.com** 域名
     → 命令进 outbox（yumaiduo_commands）

⑧ 插件执行（/opt/wanda-seat-autoquote/current）
     领取 DELIVER_TICKET 命令 → 把图片上传到闲鱼（换成 img.alicdn.com 地址）
     → 通过闲鱼会话把【图片】发给买家
     → 回写 sent_message_id / status=SENT / shipment_status=SUCCEEDED

⑨ 买家收到
     闲鱼聊天里一张图 —— 现在是 ⑤d 里① 的 canvas 模板图
     （含 影院 / 地址 / 影片 / 海报 / 场次 / 影厅 / 座位 / 取票码 明文 + 二维码）
```

## 三个必须知道的约束（都是实测过的）

| # | 约束 |
|---|---|
| 1 | **整条自动链路跑在浏览器里**（⑤ 在工作台页面执行）。操作员在取票码回来之前关掉页面 / 换电脑 / 清缓存 → **不会自动发**。 |
| 2 | **手工补发入口已按你要求删除**（原 `WandaTicketUpload.tsx` + 页面入口 + `/api/wanda-orders/{id}/ticket-card` 端点都已下线）。所以发不出去时**没有手工兜底**。 |
| 3 | **插件只认 alicdn 图片地址**（`IMAGE_HOSTS = ['alicdn.com','tbcdn.cn']`）。我们的图先经 ⑥⑦ 落到闲鱼换回 alicdn 地址才发得出去 —— 这也是为什么"直接把我们的域名喂给插件"会被拒。 |

## 目前唯一没验证的一环

**买家实际收到的那张图**。⑤d 改完之后**没有跑过一笔真实出票**，
所以"买家收到的是 canvas 模板图而不是旧版后端渲染图"这件事**还没有实证**。

**要验证的话**：走一笔真实订单（去出票 → 完成出票），然后看买家聊天里那张图 ——
需要确认用哪一笔/哪个买家，不擅自发。

## 与本仓库实现的差异（核对于 2026-10）

本仓库对应文件：`application/wanda_delivery.py`

### ✅ 已对齐

| 机制 | 线上 | 本仓库 |
|---|---|---|
| 出票必须有人操作 | `DELIVERY_NOT_ENABLED` | 同（第一道闸门） |
| 内容指纹去重 | `delivery_review_digest` | `DeliverySubmission.digest()` |
| 同单不同内容拒绝 | `TICKET_ALREADY_RECORDED` | 同 |
| 上游单号变了要拒 | `WANDA_TICKET_SOURCE_CONFLICT` | 同 |
| 改码要换版本 | `ticket_version + 1` | 同 |
| 提交 5 分钟有效 | `delivery_expires_at = +5min` | 同 |
| 交付契约 | `QR_SHIP_V1` | 同 |
| 发完码自动发货 | `SHIP_ORDER` + `TICKET_DELIVERY_NOTICE` | 同 |

### ✅ 本次按链路文档补齐（原来缺）

| 校验 | 线上位置 | 本仓库 |
|---|---|---|
| 文本与图片只能给一个 | `ONE_TICKET_MESSAGE_REQUIRED` | `DeliverySubmission.has_codes()` + `image` 唯一性检查 |
| image 键必须正好三个 | `wanda_delivery.py:71` | `validate_image()` |
| imageUrl 必须 https + alicdn | `wanda_delivery.py:73-76` | `validate_image()`（`IMAGE_HOSTS`） |
| width/height 必须 int 且 1~20000 | `wanda_delivery.py:76` | `validate_image()` |
| AUTO 必须带上游订单号 | `WANDA_ORDER_ID_REQUIRED` | 同 |

**★ 为什么 alicdn 校验必须卡**（约束 3 的直接后果）：
插件只认 alicdn 图片地址。不校验的话我们会收下一条**永远发不出去**的命令 ——
它卡在队列里，买家收不到票，而系统以为在正常处理。
⇒ 宁可在入口拒掉。

### ⬜ 本仓库没有的（且是有意不做）

| 链路里的东西 | 本仓库的处理 | 理由 |
|---|---|---|
| ⑤ 浏览器里跑自动交割 | ⬜ 无 | 我们走 **服务端队列**：出票结果交到后端 → 生成命令 → 插件来领。★ 不依赖浏览器开着。见下方「架构差异」 |
| ④ 取票码从万达接口取 | ⬜ 无 | 我们的流程是**店家在出票后台手动出票**，然后**把取票码交给系统**（`POST /api/order/deliver`）。不是系统自己去万达取。 |
| ⑤d 三级降级生成图 | ⬜ 无 | 我们只校验图，不生成图 —— 图由调用方给（对齐"正好三个键"的协议）。 |

### ★ 架构差异（重要，别搞混）

```
出票工作台（文档里那套）        本仓库
─────────────────────────      ─────────────────────────
⑤ 自动交割在【浏览器里】跑       出票结果 POST 到后端 → 落命令队列
⑥ 后端转发（FastAPI routes）     我们的 server.py 直接收
⑦ V5 wanda_delivery.submit()     application/wanda_delivery.py 同语义
⑧ 插件领 DELIVER_TICKET 执行     插件领 DELIVER_TICKET 执行（一致）

★ 关键区别：文档那套的自动交割依赖【浏览器页面还开着】；
  本仓库把这一步放在服务端队列里，页关掉也能发。
  代价是需要一个能接收出票结果的入口（已有：POST /api/order/deliver）。
```

## 排查顺序（发不出去时按这个查）

```
① 命令建了吗？        → data/plugin-queue.sqlite3 的 yumaiduo_commands
                         看有没有 DELIVER_TICKET 且 status=PENDING
② 插件领了吗？        → 同上，status=CLAIMED 说明领走了
③ 执行结果？          → status=SENT 成功 / FAILED 失败 / UNKNOWN 未确认
                         ★ UNKNOWN 不是失败 —— 是"可能发出去了但没拿到确认"，
                           插件会重试。别当失败重发（买家会收到两次）。
④ 图是 alicdn 吗？     → 不是的话插件发不出去，会被 ①②的校验拦在入口
⑤ 依赖卡住了吗？       → status=SUPPRESSED + reason=PRECEDING_COMMAND_NOT_SENT
                         说明前置命令没成功（比如改价没发出去）
```
