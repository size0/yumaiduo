## 一、401 根因（现在是源码 + 文档双重确证）

### 1.1 文档怎么说

**§1.1 协议签署表：**
```
| 《鱼麦多开发者数据处理协议》（DPA） | 手写签名 + 短信验证码 |
    → 不签的后果：插件自注册被 403 拒绝
```

**§「已经有插件在线上跑的开发者请注意」：**
```
插件每次进程启动都要自注册一次来换回 webhookSecret 与 yp_ 令牌，
签署门控对这条路径同样生效。平台为此设了一个宽限窗口——
窗口内【已注册过的插件】重启照旧放行，
但窗口结束后未签 DPA 的插件【一旦重启就会失能】：
  ★ 收到 webhook 验不了签、调不了任何接口，
  ★ 且进程不会退出，你的健康检查大概率发现不了
```

**§鉴权校验链（平台侧，任一不过即拒）：**
```
1. token 的 sha256 命中 active 凭证 → 解析 pluginId + scopes
   （否则 401 E_UNAUTHORIZED）      ← ★ 我们撞的是这一条
2. 自报租户必须已安装且启用该插件（否则 403）
3. 接口要求的 scope ∈ 凭证 scope ∩ 租户同意权限（否则 403）
4. 插件须对当前租户可用（正式 published 或有效测试窗口的 approved）
5. entitlement.feature 通过套餐门控
```

### 1.2 实测：注册端点通了

```
POST /api/v1/plugin/runtime/register
  header: x-plugin-developer-token: pdk_…（44 字符，前缀 pdk_）
  body:   { manifest, baseUrl }
  → ★ 返回 { pluginId, webhookSecret(64), token(51, 前缀 yp_) }
```
**⇒ 所以 `pdk_` 令牌有效、DPA 也签了。那个 401 就是【静态 `yp_` 令牌被撤销】。**

### 1.3 ★★★ V5 的代码漏了一半，这是它一直 401 的真正原因

```js
// register.mjs —— 原样返回整个 data（含 token），没问题
return payload?.data || payload;

// server.mjs:22 —— 用【环境变量里的静态 yp_ 令牌】建 client
if(process.env.YUMAIDUO_PLUGIN_TOKEN && process.env.YUMAIDUO_TENANT_ID)
  cfg.client = createPluginClient({..., pluginToken: process.env.YUMAIDUO_PLUGIN_TOKEN, ...});

// server.mjs:24 —— ★★★ 注册成功后【只取 webhookSecret】
registerPlugin({...}).then(data=>{ if(data.webhookSecret) cfg.secret=data.webhookSecret; })
//                                ↑ 文档说返回 { webhookSecret, token }
//                                  ★ 它把 token 扔了
```
**⇒ V5 每次启动确实注册了，但拿到的新 `yp_` 令牌被丢掉，
`cfg.client` 永远用那个已撤销的静态令牌。
所以它永远调不了平台接口（`/im/messages`、`/im/shops`、订单读取…全 401）。**

**★ 而且症状和文档描述的一模一样：**
```
「收到 webhook 验不了签」→ 其实是 webhook 还能收（靠本地 YUMAIDUO_WEBHOOK_SECRET），
                            但平台接口全挂
「进程不会退出，健康检查发现不了」→ 实测 systemctl is-active = active，一切"正常"
```
**这就是为什么这个故障能潜伏这么久：外面看着完全正常。**

### 1.4 对我们项目的意思

```
★ 这是个【必须做对】的模式，不是 V5 的八卦：
  用 pdk_ 注册 → 拿新的 yp_ 令牌 → 用它调平台 API。
  绝不能把 yp_ 写死在环境变量里 —— 它会被换掉/撤销。
  （V5 把它写死了 + 没存返回值 = 两个错叠在一起）

★ 我们现在的 ticket-agent 里【还没有】任何鱼麦多平台调用（只用 webhook 收事件），
  所以暂时没踩这个坑。等到要用 /im/messages 这类接口时，
  必须照上面这个模式做，并且【把注册返回值持久化】。
```

## 三、从真实数据推出来的意图缺口（按优先级）

### ★★★ 第 1 优先：回答数量 —— `1张` / `2张`
```
为什么最要紧：
  · 我们刚做的"张数待确认"提示，问的就是"要几个座位"
  · ★ 而买家真回答了「1张」「2张」，系统【不认识】
    ⇒ 我们问了他，他答了，我们听不懂 —— 这是最刺眼的断链
  · 而且 ticket_count 直接决定金额（报价卡按 1 张算，实际 2 张 = 报错价）
危险点：`1` 这种裸数字要和候选序号消歧
  （现有逻辑 already 把 `1` 当候选序号；只有在"等张数"的情况下才该当张数）
```

### ★★ 第 2 优先：要求改价 —— `改价`
```
买家原话就叫「改价」。而：
  · 关键词库 25 条里没有它
  · QUOTE_HIGHER 事件存在，但它的语义是【报价高于自购价 → 引导自己买】
    （QUOTED + quote.higher → SELF_BUY），不是"买家要求改价"
  · AWAIT_REPRICE 只能靠 buyer.confirm / buyer.ordered 进（卖家侧改价流程）
  ⇒ "买家主动要求改价"这条路【根本没有事件可推】，
    这不是意图层能修的，是要先定"买家要求改价该走什么流程"。
  ★ agent.py 里倒是写了 request_reprice 工具（触发词含「改价」），但没上线。
```

### ★★ 第 3 优先：问价 —— `这俩多少钱哇`
```
模型能查 read_quote（已有只读工具），所以能答。
但"这俩"指的是哪俩要靠上下文（前一条是选座截图）——
★ 这条不算断链，算"答得上但不够准"。
```

### ★ 第 4 优先：城市/影院识别 —— `陕西省西安市民乐园万达店`
```
买家直接打了地址。现在【完全没有从文字里提城市/影院的能力】：
  · 识别只从截图来
  · 意图层不做实体抽取
  ★ 而 agent.py 的 record_facts 工具就是干这个的（提取城市/影院/场次/座位）
  ⇒ 这条也不只是意图问题，是"文字里的实体"没人接。
```

### 第 5：选座意向 —— `想要这两个位置的` / `灰色的座位可以选是吗`
```
"灰色可不可以选"已有关键词。
"想要这两个位置的"其实是【指了指截图上的两个座位】——
★ 这需要"从对话里推断买家指了哪两个座"，我们没有这个能力。
```
