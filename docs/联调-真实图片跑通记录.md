## 一、本地测试方法（鱼麦多文档 §9.1）

文档原文说的两条自测能力：

```
· Manifest 校验：本地起插件进程时若 manifest 不合规，
  自注册接口会用与平台注册【同一份】规则把错误字段逐条回执
· 插件侧逻辑自测：用示例插件自带的 mock-webhook.mjs 给本地进程
  灌入一条「签名后的」事件，验证验签、事件解析、关键字匹配与幂等
  —— 全程无需平台参与
```

**★ 我们仓库里没有 `mock-webhook.mjs`**（那是官方示例插件带的）。
但我们有等价的本地工具，而且更贴业务：

| 工具 | 干什么 | 用法 |
|---|---|---|
| `chat.py` | 交互式对话（**`/img <URL>` = 买家发选座截图**） | `python chat.py --live --chat probe` |
| `chat.py`（不加 --live） | 同上，但用假 api，**不花钱不下单** | `python chat.py` |
| `simulate.py` / `simulate2.py` | 批量回放线上真实买家消息 | `python simulate2.py --only 问价` |
| `simulate_ctx.py` | 带上下文的短回复（"1"、"2张"、"改价吧"） | `python simulate_ctx.py` |
| `replay_case.py` | 回放真实案例（识别结果用线上真 payload） | `python replay_case.py` |

**★ `chat.py` 的 `/img <URL>` 就是"买家发了这张选座截图"** —— 这是最直接的联调入口。

### 1.1 ★ 图片可访问性（踩到的第一个坑）

```
直接 urllib 抓 alicdn → HTTP 420（反爬）
带浏览器 User-Agent → HTTP 200，48886 字节，image/jpeg
```

**★ 但这不影响良票识别** —— 识别是**良票侧去抓图**（文档：「模型侧直接读取，
平台不下载」），它自己的出网条件能抓到。实测确实抓到了。

## 四、★ 顺带查出并修掉的一个真问题

**现实现象：**
```
state=已报价(QUOTED)  但  recognition_id=None
候选维度=['cinemas','movies']  但  候选文本=''
```

**根因：**
```python
# recognition_id 原来只在 _ask_candidate 里存
# 而 _ask_candidate 只在【没收敛】时被调
⇒ EXACT 时 conv.recognition_id 一直是 None
```

**对 EXACT 本身不错**（不需要二次确认），但两件事会出问题：
```
① 多轮消歧每一轮都靠二次确认推进 —— 句柄一丢整条链就断
② 排查时看不出"这次识别到底有没有句柄"：
   None 分不清「平台没给」还是「我们没存」
```

**修法：把 `recognition_id` / `city_name` 提到 `_after_recognition` 统一存**
（并删掉 `_ask_candidate` 里的重复写入 —— 两处写同一个值，
将来改一处忘另一处就会不同步）。

**修完实测：** `recognition_id = 447486`（有了）。

## 六、下次怎么安全地做这种联调

```
★ 要跑真识别（花识别费，但不涉及资金）：
    chat.py 或直接调 api.ch7_recognize(...)
    ★ 识别失败不扣费（文档明确）

★ 要跑到报价（免费）：
    调 on_message(image_url=...) 就够 —— 它只做 识别 + preflight + 算价
    ★ preflight 文档明确「不建单、不冻结、免费」

★★ 绝对不要碰的（会真花钱）：
    on_buyer_confirm / ch5_create / 任何带 "create" 的调用
    —— 除非明确知道要下这一单

★ 想全链路演练又不花钱：
    chat.py 不加 --live（注入假 api）
    chatex.py（报价/下单都是假函数注入）
    tests/ 下所有带假 transport 的套件
```
