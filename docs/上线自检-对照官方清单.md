## 二、本次修掉的（核清单查出来的）

### ① `/healthz` 缺 `registered` 字段

```
官方 §14 / §9.3：GET {baseUrl}/healthz 返回 { ok:true, registered:true }
我们原来：        { ok:true, mode:"shadow" }        ← 缺 registered

为什么重要：这是平台和你的【自检端点】。
  注册失败时（比如 vendor 不符 403、没签协议、网络不通），
  原来只 console.error 一行，很容易被漏掉；
  现在 /healthz 直接回 registered:false + registration.state=FAILED + error。
```

**改完实测：**
```
正常：      {"ok":true,"registered":true,"mode":"shadow","registration":null}
注册失败：  {"ok":true,"registered":false,"mode":"shadow",
             "registration":{"state":"FAILED","error":"fetch failed"}}
```

### ② 注册状态没被跟踪

`server.mjs` 原来 `.then(data => { if (data.webhookSecret) cfg.secret = ... })`
—— 成功/失败都没留痕。现在记 `cfg.registration = {state, error}`。

### ③ ★ 我改 ① 时改出了新 bug（也修了）

```
我把新增的几行挤成了一行，字面 "\n" 进了 JS 文件 ⇒
recoveryInspected 的声明被吞掉 ⇒ 插件每轮报：
    pending command drain failed  recoveryInspected is not defined
⇒ 命令队列全废（插件活着但什么都不做）
```

**教训**：JS 文件里不能靠脚本塞 `\n`；改完必须 `node --check` + **真跑一遍看日志**。

## 四、§13 开发红线对照

| # | 红线 | 我们 |
|---|---|---|
| 1 | 插件是独立进程，禁止 import 平台核心模块 | ✅ 独立 node 进程，只走 HTTP |
| 2 | `dependencies` 只能是 SDK 三件套 | ✅ `package.json` 依赖只有 `json-bigint`（SDK 在 `vendor/`） |
| 3 | `permissions[]` / `subscribes[]` 只能从白名单选 | ✅ 人工核过（10 + 5 项都在白名单） |
| 4 | 配额 key 必须 `{id}.` 前缀；菜单/路由 `/console/plugins/{id}/` | ✅ 我们没用配额；无自定义菜单路由 |
| 5 | `manifest.vendor` 必须等于你的 vendor | ⚠️ **待确认**（见 P1 ⑤） |
| 6 | webhook 必须用 header 时间戳 + raw body 验签；长任务原子持久入队 | ✅ 验签对（raw body + header 时间戳）。★ **但 ACK 时机要注意**：插件的顺序是 `verify → attachOrderDetail → 转发我们 → drain() → 才回 202`。官方要求 **5 秒内回 2xx**，否则平台熔断。drain 里有外部调用，**这是上线后要盯的地方** |
| 7 | `quota` 只管自定义额度；真实收费只用 `billing` | — 不适用 |
| 8 | 扩展字段走 `updateExtension` | — 不适用 |
| 9 | 前端无内联脚本；不直连平台 SSE | ⚠️ UI 未实现 |
| 10 | 业务参数错 4xx；临时故障 5xx/429 | ✅ 我们：验签失败 401、参数错 400、未配置 503 |
| 11 | 禁止用租户控制台 JWT 调 `/api/*`；IM 走插件 API `X-Plugin-Token` | ✅ 我们不用 JWT |

## 五、★ 一个必须盯的风险：webhook 的 5 秒预算

官方 §7.2：
> 响应预算 5 秒：平台出站请求 5 秒未收到响应即判超时中止。
> 超时/网络错误/5xx/408/429 → 指数退避重试（5s 起，上限 5min），同一事件最多 6 次。
> 连续多次失败会被**熔断**（每 60 秒只放 1 条探测）。
> 死信**不自动补投** —— 漏掉的数据要自己用 `orders.list` 对账。

而插件的处理顺序是：
```javascript
verify(rawBody, req)                    // 本地，快
await attachOrderDetail(...)            // ★ 读鱼麦多官方订单（外部调用）
const out = await backend('/api/v1/events', ...)   // ★ 转发我们（超时 15s！）
if (out.status < 400) await drain()     // ★ 领命令 + 执行 + 报回执
res.writeHead(202)
```

**风险点**：
```
· 转发我们的超时是 15 秒（V5_BACKEND_TIMEOUT_MS 默认 15000），
  比平台的 5 秒预算【长】⇒ 我们慢了会导致平台侧超时
· drain() 里有外部调用（鱼麦多 API），也可能拖长
```

**我们侧做了什么**：`/api/v1/events` **只落库不处理**（处理在 `run-due`），
所以那条请求本身很快。**但 `drain()` 在同一个请求里**，它不受我们控制。

**建议**：
```
① 把 V5_BACKEND_TIMEOUT_MS 调到 3000（小于平台 5 秒预算）
② 上线后看插件日志有没有 "pending command drain failed" —— 那是熔断前兆
③ 用 orders.list / im.listMessages 对账，别指望平台重放死信
```

## 六、怎么用这份自检表

```powershell
# 1) 起我们的后端
cd E:\200行的agent\ticket-agent
D:\python\python.exe server.py            # 8801

# 2) 起插件（指向我们）
$env:V5_BACKEND_URL="http://127.0.0.1:8801"
$env:YUMAIDUO_WEBHOOK_SECRET="<界面上的密钥>"
$env:YUMAIDUO_COMMAND_MODE="shadow"       # 先 shadow 演练，不碰闲鱼
$env:YUMAIDUO_TENANT_ID="<你的租户>"
$env:PLUGIN_EXECUTION_JOURNAL_DIR="E:\...\journal"   # live 模式必须是绝对路径
node yumaiduo/plugin-runtime/src/server.mjs

# 3) 自检
curl http://127.0.0.1:4015/healthz
#   期望：{"ok":true,"registered":true,...}

# 4) 跑体检
D:\python\python.exe run_checks.py
```
