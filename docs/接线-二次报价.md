## 一、★★ 想清楚的关键：优惠减在哪个基数、会不会亏

设置三项（按 label 直读）：
```
enabled           要不要做二次报价
wait_seconds      等买家拍下多久（超时就再报一次）
discount_percent  优惠比例（%）—— min 1 / max 10
```

**最容易错的一件事**：报价里其实有三个金额
```
total_price_fen   给买家的报价（含毛利）
cost_total_fen    我们的成本（要付给渠道的）
margin_total_fen  毛利 = 报价 − 成本
```
**如果盲目按"报价 × 3%"减**：
```
报价 100.00、成本 99.00（毛利 1.00）⇒ 减 3.00 ⇒ **亏 2.00**
```

**⇒ 我定的规则（保守、不亏）**：
```
优惠 = min(报价 × 比例, 毛利)     ← 最多把毛利让完
最坏情况是"不赚钱"，绝不"倒贴"。
毛利 ≤ 0 ⇒ 不给优惠（再减就是亏）。
```

**★ 基数选了"报价总额"而不是"毛利"**：
买家看到的是总额，优惠 3% 也是对总额说的。
按毛利减的话，3% 的毛利可能只有几分钱，**买家根本感觉不到，这个功能就白做了**。

## 二、★★★ 实测抓到一个"骗买家"的 bug

```python
# 我第一版（引擎里，毛利 ≤ 0 时）
return _replace(base, notes=notes)     # ← 造了个新对象，只是 notes 不同
```
而调用方是靠 **`new_quote is quote`** 判断"有没有真的让利"的：
```
⇒ 造了新对象 ⇒ 调用方以为让了利 ⇒ 发出
  "这个价格我再给您让一点：现在 100.00 元（已再优惠 3%）"
  —— 而金额一分没少。
```

**这是我实测第 5 个用例时抓到的**（毛利为 0 的场景）。
**⇒ 修：毛利 ≤ 0 时【原样返回同一个对象】**（`return base`），
调用方就判得出"让不出优惠"，于是**不发那条消息**。

> **★ 教训**：用"对象身份"当判据时，**任何造新对象的路径都会破坏它**。
> `_replace` 看着无害（只改了 notes），但它把身份变了。

## 五、★ 一个设计取舍：不重发报价卡，只发一句话

**为什么**：重发报价卡需要**原始的识别结果**（影院/影厅/座位/场次…），
而那是几分钟前的东西，**进程重启后就没了**。硬发会缺字段。

**⇒ 这条只说【新价格】，同时把会话上的报价也改成新价**：
```
conv.quote = new_quote
⇒ 之后下单/改价自然用新价，金额不会前后不一致。
```
