# 良票「识别失败原因」实际有哪些 —— 查文档的结论

> 起因：同业预览里 RECOG_FAIL 有 7 个码，其中「座位数量超限」「座位被遮挡」
> 我们不确定良票到底会不会返回这两种原因。
> 查证对象：良票开放平台 API 接入文档（1399 行）
> 日期：2026-10-13

---

## 〇、结论（先说结果，因为它推翻了我的假设）

```
★★★★ 良票【不会】返回「座位数量超限」和「座位被遮挡」这两种识别失败原因。
```

**这两个场景是真实存在的，但发生在【询价 / 下单阶段】，不是识别阶段。**
**⇒ 把它们挂在 RECOG_FAIL 上、并放在识别流程里触发，是错的。**

---

## 一、识别接口真正会返回的原因

### 1.1 `noMatchReason` —— 只有两个值

| 取值 | 含义 | 文档给的处理建议 |
|---|---|---|
| `SHOW_EXPIRED` | 截图里的场次已经开场了 | 提示「场次已开场」并让用户换一张截图。**重试、补 cityName、走二次确认都不会有值** |
| `NOT_FOUND` | 影院影片都定了，但排片里没有这个时间点的场次 | 可能暂未开售或影院未接入，引导用户改走手动选座 |
| `null` | 没走到「按场次匹配」这一步 | 看 `matchLevel` 与 `candidates` |

**★ 没有座位类原因。**

### 1.2 识别错误码 70xxx —— 只有 9 个

| 码 | 含义 |
|---|---|
| `700001` | 识别服务未配置或已停用 |
| `700002` | 图片地址无法访问（**你侧问题**，检查防盗链与有效期） |
| `700003` | 识别超时 |
| `700004` | 模型服务异常 |
| `700005` | 识别结果无法解析 |
| `700006` | 图片不是选座页截图 |
| `700007` | 识别任务不存在 |
| `700008` | 识别记录不存在或已过期 |
| `700009` | 所选候选无效 |

**★ 依然没有座位类原因。**

### 1.3 `matchLevel` —— 决定能不能直接下单

| 取值 | 含义 | 该怎么做 |
|---|---|---|
| `EXACT` | 唯一命中场次 | 直接用 `showId` 走询价/下单 |
| `CANDIDATE` | 影院/影片/场次没收敛到唯一 | 从 `candidates` 里挑，走二次确认 |
| `NONE` | 影院或影片在标准库里没找到 | 补 `cityName` 重试 |

## 二、「座位数量超限」的真相：`maxSeatsPerOrder`

**良票文档 §4 座位图原文（748 / 770 行）：**

```
| maxSeatsPerOrder | number | 本场次单笔限购座位数(1~6) |

maxSeatsPerOrder 是本场次的单笔限购座位数，由供货方决定、可能低于平台上限 6
（部分供货方单笔仅支持 4 张）。请在选座交互上就按它限制数量：
★ 超过限购的订单会在【出票环节】被拒。更多座位的需求请分多笔订单。
```

**⇒ 不是识别失败，是出票环节被拒。而且等到出票才拒，买家已经付过钱了。**

---

## 三、「座位被遮挡」的真相：其实是「隔空选座」违规（200007）

**良票文档 §4 座位图原文：**

```
选座需遵守两条行业规则（违反报 200007）：
  情侣座必须成对且相邻购买；
  ★ 一排连续有效座位超过五个时，不允许在所选座位任一侧留下单个空位（隔空选座）。

平台在下单时按实际履约供货方的原始座位图预校验：
  物理结构（相邻/一左一右/隔空）逐排进行，坐标完整的排照常校验，
  缺坐标的排跳过、由供货方锁座裁决 —— 违规同样会导致出票失败。

预校验在下单接口内【同步】进行：所有候选供货方的座位图都判定违规
（座位已售报 200006，孤座/情侣座违规报 200007）时，下单直接同步报错，
不占用余额、不产生订单回调。
隔空选座的报错会点名被夹出的空位（如「不能留下单个空座(D排5座)，请重新选择或加购该座位」）
```

**⇒ 同业文案写的「座位被遮挡」是通俗说法，真实含义是**
**「一排连续座位超 5 个时，你说的座位任一侧留了单个空位」**（也含情侣座不成对）。

**★ 相关错误码：**

| 码 | 含义 | 文档建议 |
|---|---|---|
| `200005` | 场次已停售 | 已过截单时间 |
| `200006` | 所选座位不可用 | 重新拉座位图 |
| `200007` | 选座不符合规则 | 见座位图一节的两条行业规则 |

## 四、因此做了什么改动

### 4.1 ★★ 把 200006 / 200007 / 200005 / 300006 接到【询价 + 下单】两个分支

```python
# 询价分支（_quote_via_liangpiao）
except LiangPiaoError as exc:
    code = getattr(exc, "code", 0)
    if code == 200006:      → seat_taken    "您选的座位刚被别人买走了"
    elif code == 200007:    → seat_blocked  "识别到座位被遮挡，请重新选座"
    elif code == 200005:    → show_stopped  "这个场次已经停售了"
    elif code == 300006:    → price_changed "票价刚变了，得重新报价"
    else:                   → 默认 "这个场次暂时询不到价，请稍后再试"

# 下单分支同样接 200006 / 200007 / 300006
# ★ 同一个错，不管在哪一步被拒，给买家的话必须一致
```

### 4.2 ★★ 补上 `maxSeatsPerOrder` 守卫（询价前就拦）

```python
# _quote_via_liangpiao，在调 preflight 之前
limit = result.max_seats_per_order
if limit and len(seats) > int(limit):
    out.ok = False
    out.add("RECOG_FAIL", {"_variant": "seat_limit",
                           "fail_reason": f"这个场次一笔最多买 {int(limit)} 张"})
    out.notes.append(f"maxSeatsPerOrder={limit}，选了 {len(seats)} 张 —— "
                     f"在询价前拦下（否则会在出票环节被拒，得退款）")
    return out
```

**★ 为什么值得单独拦（而不是等上游拒）：**
```
等到出票环节才拒，买家已经付过钱了（我们这边已经落单）—— 那是要退款的。
在询价前用【已有数据】拦一下，成本为零。
```

**★★ 找不到这个字段、或这个字段是 None 时【不拦】：**
```
不能拿"默认 6"当依据 —— 那是编的。
文档说明：仅 EXACT 且已拉座位图时 maxSeatsPerOrder 才有值。
```

**★ 顺带发现的老问题：**
```
integrations/liangpiao/api.py:333  max_seats_per_order=int(data.get("maxSeatsPerOrder") or 6)
integrations/liangpiao/api.py:411  max_seats_per_order=f.get("maxSeatsPerOrder")
★ 解析出来了，但全仓搜索【没有任何地方用它】——
  也就是说从来没按场次限购拦过，全靠上游在出票环节拒绝。
```

### 4.3 新增 2 个变体（都不是"识别失败"，但复用同一条模板）

| 变体 | 场景 | 文案 |
|---|---|---|
| `seat_taken` | 200006 选中的座位在下单那一刻被买走 | 亲，您选的座位刚被别人买走了~\n辛苦重新发一下选座截图，我按新的座位给您报价 |
| `price_changed` | 300006 询价后、下单前票价变了 | 亲，票价刚有变动，之前那个价格下不了了~\n辛苦重新发一下截图，我给您重新报价 |

**★ 为什么复用 `RECOG_FAIL` 这条模板：**
这是同一个"这单没成，要买家做点什么"的位置，拆新模板会让状态机的
"哪些码归哪条文案"变复杂。用变体区分场景，既统一了入口又能说对话。

## 五、★ 我们的 `_recog_fail_reason` 对照 —— **已补齐**

```python
def _recog_fail_reason(code: int) -> str:
    return {
        700002: "图片没能读取到，麻烦重新发一下截图",
        700003: "识别超时了，麻烦再发一次",
        # ↓ 2026-10-13 新补
        700004: "识别服务刚才有点忙，麻烦再发一次截图",
        700005: "这次没能读出来，麻烦重新发一次截图",
        700006: "这张图好像不是选座页截图",
        700008: "识别记录已过期，请重新发截图",
        700009: "刚那个选项对不上了，麻烦重新发一次截图，我给您重新列一遍",
    }.get(code, "没能识别出座位信息")
```

**★ 文案的判据不是"好听"，是【买家知道该做什么】：**

| 码 | 文档建议 | 我们的文案 | 为什么 |
|---|---|---|---|
| `700004` 模型服务异常 | 重试 | 识别服务刚才有点忙，麻烦再发一次截图 | ★ 这是**平台侧临时故障**，不是买家的图有问题 —— 说"你的截图不对"会让买家白白重拍好几遍 |
| `700005` 识别结果无法解析 | 重试 | 这次没能读出来，麻烦重新发一次截图 | 同上 |
| `700009` 所选候选无效 | 只能从本次识别返回的候选里挑 | 刚那个选项对不上了，麻烦重新发一次截图，我给您重新列一遍 | ★ 买家的图和他的选择**都没错**，只是候选过期了 —— 让他重发图是过重的处置 |

### 5.1 ★★ `700009` 还做了一件事：优先重发候选，而不是报错

```python
# _after_recognition 的二次确认分支
except LiangPiaoError as exc:
    if getattr(exc, "code", 0) == 700009:
        options_text = getattr(conv, "last_candidates_text", "")
        if options_text:
            out.ok = True
            out.add("DISAMBIG", {"candidates": options_text, "pick_kind": ...})
            return out        # ← 买家接着挑，【不用重走识别】
        out.add("RECOG_FAIL", {"fail_reason": _recog_fail_reason(700009)})
```

**★ 为什么重发候选比报错好：**
```
① 买家的图和他的选择都没错，只是候选对不上了 —— 重发一次他就能接着挑；
② 重走识别要【再花一次识别费】（良票按次计费，AI_USAGE 流水）。
   手里已经有候选表（conv.last_candidates_text）就不用再花钱。
★ 但手里没有候选表时（比如进程重启过）→ 只能让他重发，
  这时用 _recog_fail_reason 的统一文案，不另写一套 —— 同一个码两套说法会混乱。
```

**★ 顺带修掉的一处不一致：**
```
原来这里硬编码了一句「这个选项已经不能买了，请重新发截图」，
和 _recog_fail_reason 的文案表各说各话。
现在统一走 _recog_fail_reason，改文案只用改一个地方。
```

## 附：这次查证的方法

```
1. 先看良票文档的错误码总表（183 行起）—— 50 多个码，按模块分段
2. 再看 §7 选座截图识别的 noMatchReason 表 —— 只有 2 个值
3. 找「座位数量超限」「座位被遮挡」这两个词在文档里的出处 —— 都搜不到
4. 反查座位图 §4 —— 找到 maxSeatsPerOrder（限购）和 200007（选座规则）
⇒ 结论：那两个场景真实存在，但属于【下单/询价】阶段
★ 教训：同业文案的场景标签是业务语言，不是接口字段。
  要对齐的是"买家看到什么"，不能反推成"接口会返回什么"。
```
