## 一、先钉住三个事实（都是从数据/代码里抠出来的）

### 事实 1：两条渠道的"确认"代价【完全不同】

```
良票：ticket_flow.py:1376  created = self.api.ch5_create(...)
      ⇒ 真的向良票建单、真的冻结资金
      文档：响应 status 通常为 SUBMITTING，带 freezeAmount
      文档：300010「同一场次座位完全相同且已有提交的订单处于出票中」（防重复提交）
      文档：5.5 订单拦截「进入出票中(TICKETING)之后不可拦截」
      文档：500001「该订单的供应商【不支持退票】」← 这就是"无法取消"的那类
            5.7「退票是异步的，而且【可能退不成】」

万达：on_buyer_confirm → 只是本地落一条单，
      代码原文：「万达：店家【手动出票】，插件不调任何下单接口」
```

**★ 所以"必须校验金额"这条纪律的严格程度，两条渠道不一样：

## 三、我的处理方案（逐类）

### 3.0 总原则：**模型负责"懂"，代码负责"动"，金额负责"拦"**

```
① 模型：把你的话变成结构化的意图 + 事实（意图集合封闭、可审计）
② 代码：意图必须合法（状态机白名单）、张数必须 1~6、影院/场次必须真实存在
③ ★ 金额门：动钱之前，代码重新算一遍金额，和买家确认过的那个数【逐分比对】
```

### 3.1 ★★★ 金额门（你说的那条，我做成三道）

```
第一道：报价时把金额【记进会话】
   conv.quote = quote（已有）  ← 包含 total_price_fen / seat_count /
                                 max_price_fen / ticket_mode / quote_channel

第二道：买家确认时，拿【他自己报的张数】重算，比对
   现在的问题：报价卡是按 1 张算的（没选座时 count 兜底成 1）
   买家回「2张」⇒ 必须重算成 2 张的金额，再让他确认一次那个新金额
   ★ 不能拿 1 张的报价去下 2 张的单

第三道：下单前逐分核对
   before = conv.quote.total_price_fen
   now    = 用 conv.quote_params 重新算一遍（同规则、同参数）
   if before != now:  → 拒绝下单，重新报价给买家确认
   if 张数 != 买家确认的张数: → 拒绝下单
   if 渠道 == 良票 and maxPrice < 应付: → 拒绝（否则良票 300005）
   ⇒ 任何一条不过，都不调 ch5_create
```

**★ 为什么必须在下单【之前】做，而不是靠拦截**：
```
文档 5.5：进入出票中(TICKETING)之后不可拦截
文档 500001：该订单的供应商不支持退票
文档 5.7：退票是异步的，而且可能退不成
⇒ 拦截/退票都是【补救】，不是保证。
  唯一可靠的时机是 ch5_create 之前。
```

### 3.2 逐类怎么回、怎么处理

| 买家说什么 | 怎么回 | 怎么处理 | 依据 |
|---|---|---|---|
| **「2张」「两张」「1」** | 复述：「好，2 张。我按 2 张给你算，等我一下~」 | 模型抽 quantity → 代码校验 1~6 → **重算价** → 出新的报价卡 | 391 条 |
| **「好」「OK」「可以」「对」** | **不直接下单**。回：「好~ 我确认一下：XX影院 XX片 XX场 座位XX **共 X 张 / X 元**，回复"确认"我就下单哦」 | 等买家回"确认"（逐字命中已有的 `_is_confirm`）→ 走既有 `on_buyer_confirm` | 1001 条；★ 金额门在此生效 |
| 「多少钱」「什么价」 | 有报价 → 报给他；没有 → 「发我选座截图就给你算」 | 只答话，不动状态 | 463 条 |
| 「多久出票」「还没好吗」 | 照**实际档位**答（`ticket_window`），有订单就报订单状态 | 只答话 | 43 条 |
| 「怎么买」「怎么拍」 | 固定话术：拍下→先别付款→我改价→收到通知再付 | 只答话 | 37 条 |
| 「这个可以买吗」 | 有识别结果 → 查可售性再答；没有 → 要截图 | 只答话 | 132 条 |
| 「你好」「在吗」 | 短句招呼 + 引导发截图 | 只答话 | 468 条 |
| **城市/影院/场次打字** | 复述确认：「你是要 XX 影院 XX 片 XX 时间对吧？」 | 模型抽实体 → 良票查影院 + 万达查排片 → 校验通过才用来报价 | 442 条 |
| **「人工」「转人工」** | 「好，这就给你转人工~」 | `need_human = True`，**立即转** | 32 条 |
| **「退款」「不要了」** | 「我帮你转人工处理，稍等~」 | **绝不自动退款**。转人工 + 把订单/refundable 一起给人看 | 30 条 |
| **「改价」「便宜点」** | ★ 待你定（见 §四） | ★ 待定 | 102 条 |
| 表情、符号 | 不单独回（或极短） | 无 | 123 条 |
| 长尾（34%） | 模型答；拿不准就转人工 | 只答话 | ~1891 条 |

### 3.3 ★ 顺便治一个真问题：把那个 LLM 的嘴管住

**现在买家看到的很多是 140~353 字的 markdown 长篇（带 `**粗体**`、编号列表）。
闲鱼是聊天界面，那样很怪，而且容易说错话（已经泄漏过内部备注、误发过快递通知）。**

```
建议给那个 LLM 加三条硬约束（★ 我们仓库里的 conversation_ai.py 已经有这套，
  就在 prompts/ 与 HARD_RULES 里，直接复用同一份约束文本即可）：
  ① 单条回复 ≤ 60 字，不用 markdown、不用编号列表
  ② 不许编价格、票码、场次 —— 只许引用系统给的事实
  ③ 拿不准就说「我帮你转人工看下」，不许自己发挥
★ 我们 `conversation_ai.py` 的 HARD_RULES 就是这套，
  而且它有【只读工具】能查订单/报价/FAQ —— 比那个自由发挥的 LLM 安全。
```

## 四、要你定的（就一件，其余我都能定）

```
买家说「改价」「便宜点」（102 条），你要哪种？
  A. 重新算一次价报给他（按当前规则）
  B. 什么都不回，直接转人工让你决定
  C. 告诉他"你先拍下，拍下后我给你改价"（闲鱼上通常这么做）
  ★ 我倾向 C —— 因为线上实际发生的就是"拍下→改价→付款"，
    而且 C 不涉及"先改价后买家不买"的风险
```

## 五、我建议的动手顺序

```
第 1 步（最要紧）：金额门
   · 把金额/张数/档位/渠道 都记进会话（大部分已有）
   · 下单前逐分比对，不过就不调 ch5_create
   · ★ 这条不依赖任何"怎么回"的决定，纯安全，先做

第 2 步：数量意图（391 条）
   · 模型抽 quantity，代码校验，重算价 → 出正确的报价卡
   · ★ 它是金额门的前提（张数不对，金额必错）

第 3 步：转人工 + 退款 → 一律不自动处理（32 + 30 条）
   · 这两类风险最高、实现最简单

第 4 步：确认意图（1001 条）
   · 模型认到 → 复述金额 → 等"确认" → 走既有下单路径

第 5 步：实体抽取（442 条）+ 管住那个 LLM 的话
```
