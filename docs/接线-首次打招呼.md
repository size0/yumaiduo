## 一、★★★ 真 bug ①：picker 控件改了什么都存不下去

```javascript
// web/config.js（改前）
picker(c) {
  const btn = el('button', {...});
  btn.addEventListener('click', () => {
    const box = prompt(...);
    if (box !== null) btn.dataset.value = box;   // ← 写进按钮的 dataset
  });
  return el('div', {...}, [ btn ]);              // ← 没有 <input data-key>
}
```

而 `collect()`（保存时收集表单值）只遍历 **`[data-key]` 的 `<input>`**：
```javascript
$$('[data-key]', sec).forEach(input => { ... });
```

**⇒ 按钮上的 `dataset.value` 根本没人读 ⇒ 这个控件存不了任何东西。**

**它看起来完全能用**：会弹窗、会回显你输的字。
**但保存后重新加载，值就没了。**

**影响两个设置**：`reply.greeting_configured`（首次打招呼）、
`order_refund.return_info`（退货信息）。

**修法**：生成真的 hidden input（带 `data-key`），弹窗结果写进它的 value。

## 二、★★★ 真 bug ②：hidden input 一律转布尔，会把字典写成 false

```javascript
// collect()（改前）
if (input.type === 'hidden') {
  bucket[k] = input.value === '1';    // ← 一律布尔
  return;
}
```
**而 `return_info` 的默认值是字典 `{}`** —— 一律转布尔会把它写成 `false`，
**把配置覆盖坏**。

**⇒ 改成按【原值类型】转**：布尔 → `'1'`/`''`；字典/列表 → JSON；其它 → 原样字符串。
用 `data-vtype` 记住原类型。

## 三、接了首次打招呼

**语义（从字段拆出来）**：
```
greeting_configured      打不打招呼（默认 False ⇒ 默认行为一个字不变）
greeting_message_types   什么类型的消息算"进来"（默认 文字+图片）
greeting_interval_hours  间隔多久才【再】打一次；0 = 不限制
GREETING 模板            说什么（店主确认过的口径）
```

**★ 为什么"只在首次"很重要**：每句话都回一遍"你好"就不像人了，
而且会打断正常流程（买家问"多久出票"，你回一句"你好"）。

**★ 为什么是【追加】不是返回**：打招呼不该拦住正常流程 ——
买家发选座图，我们照样识别+报价，只是多一句招呼。

**★ 为什么放 `_finish`**：`on_message` 有 **11 个返回点**，
每个都改早晚漏一处。所有出口都过 `_finish` ⇒ 一处就够。
（实测：11/11 都带上了参数。）

**★ 只有【真发出去】才记时刻** —— 否则一次异常会把"已经打过招呼"
永久写进会话，以后再也不打。所以要落盘（重启不忘）。

### 四条不猜的取舍

| 取舍 | 做法 | 理由 |
|---|---|---|
| 空 `greeting_message_types` | **不限制**（不是"什么类型都不打"） | 按"都不打"理解，配置一被清空招呼就永远发不出去 |
| 时刻存坏了 | **当作没打过**（宁可多打一次） | 不能因为一个坏字符串把功能永久关掉 |
| 间隔 `<= 0` | **不限制** | 显式表达"每次都算首次" |
| 判定位置 | **`_finish` 统一追加** | 11 个返回点，逐个改必然漏 |

## 四、★ 我自己踩的坑：`except: pass` 把"名字写错"吞掉了

我在 `_finish` 里写了：
```python
_gtext = tpl.text_for("GREETING", ...)
```
**但 `service.py` 里根本没有 `import templates`。**
`tpl` 是个未定义的名字 ⇒ 抛 `NameError` ⇒
**被我自己写的 `except Exception: pass` 静默吞掉。**

**结果**：打招呼永远发不出去，而且**一点报错都看不到**。
我花了三轮才定位到（`_greeting_due` 返回 True、
`_finish` 直调又正常、`on_message` 里却不生效 —— 全靠一层层探针）。

**★ 两个教训**：
```
① `except: pass` 会把"名字写错"和"真的发不出去"混成一件事。
   兜底可以"不影响主流程"，但【必须留痕】。
   ⇒ 现在改成记一条 note（"★ 打招呼没发出去（不影响回复）：NameError…"）
② 我自己写的"兜底"反过来掩盖了我自己的 bug。
   ★ 宽 except 是双刃剑 —— 它保护主流程，也保护 bug。
```

**另一个教训**：`on_message` 最后走的是 `_answer_with_ai`，
而**它内部自己调 `_finish`** —— 我批量改的 11 个返回点里
**不包含这一条**。⇒ 参数要一路传下去才算接完。

## 六、★ 审计的读取模式已经第五种了

`_check_settings` 要判"这个字段有没有人读"，而实际代码里有五种写法：
```
① cfg.section.key                     点号链
② getattr(cfg.section, "key", d)      紧邻 getattr
③ cfg = load().section + getattr(...) 跨行
④ ti = getattr(cfg, "section") + ...  对象传参
⑤ rs = cfg.section + getattr(rs, "k") 先赋局部名     ← 本轮新增
```
**★ 已经五种了。** 我在注释里写了：
> 与其不断加正则，不如让业务代码统一用一两种写法。

**★ 而且窗口大小是"猜"的**：我把窗口设 300 字，
而实际的 `rs = cfg.reply` 到 `getattr(rs, "greeting_interval_hours")`
**隔了 482 个字符**（中间是我写的注释）⇒ **假失败**。
> **假失败和真失败长得一模一样**，都要靠手算距离才能区分。
