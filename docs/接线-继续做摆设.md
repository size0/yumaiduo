## 二、消息延迟：加在【命令层】，一处管全部

**为什么不在各个发消息的地方各写一遍**：发消息的入口有十几处
（`plugin_runtime` / `reminders` / `agent`…），逐个加必然漏。

```python
def _apply_message_delay(cmd):
    """任何要发给买家的消息，入队前把 not_before 往后推一点。"""
```

**机制**：设置命令的 `not_before`。
插件的 `claim_pending` **早就支持"没到时间不给领"**
（`tests/_check_plugin_queue.py` 里就有一条这样的断言）
⇒ **不用改插件、也不用 sleep 阻塞任何人**。

**实测**：
```
关闭（默认）：SEND_MESSAGE 的 not_before = ''      ← 一点不改行为
打开 300ms ：not_before 距现在 0.30 秒
改价命令    ：not_before = ''                      ← 改价不该拖（趁早做更好）
已有时间的不被覆盖：2099-01-01T00:00:00+00:00 ✓
```

**★ 只对"要发给买家的消息"生效**（`SEND_MESSAGE` / `TICKET_DELIVERY_NOTICE`）；
改价、发货这类不加延迟 —— 那些是趁早做更好的事，拖慢没意义。

**★ 取 min_ms 而不是随机**：随机更像人，但会让"同一句话两次延迟不同"
变得不可复现，排查问题反而麻烦。`settings` 里有 `max_ms`（隐藏字段），
以后要用再一起接。

## 三、自动退款：先搞清语义，再决定接什么

**`auto_refund_on` 的定义里写着**（不是我猜的）：
```
options = [出票失败, 校验金额/改价失败, 创建订单失败, 无有效报价记录]
hint    = "勾选的情况会自动退款，未勾的需要人工处理"
```

**★ 但退款其实是良票平台自动做的**（回调里带 `refundAmount` / `lossAmount`），
**我们拦不住** ⇒ 这个开关真正能决定的只有两件事：
```
① 我们对买家说什么
② 要不要转人工
```

**接线**：
```
勾了「出票失败」  ⇒ 照旧发那句话（"系统已自动给你退款"）—— 这是事实
没勾              ⇒ ① 不替平台承诺退款
                    ② 明确标"需人工处理"
                       （否则买家以为系统会退钱，在那儿等着）
```

**★ 判不出是哪一种时，按人工处理**，绝不瞎猜成"出票失败" ——
猜错就等于替平台承诺退款。

默认勾着「出票失败」⇒ **默认行为一个字不变**。

## 四、识别关键字：这是**代码自己承诺了但没做**的一处

`_parse_pick` 的 docstring 写着：
> ★ 关键字本身也是可配的（`settings.recognize_quote.keyword_*`），
>   所以这里做前缀匹配而不是写死。

**而代码里就是写死的** `("影院","影城")` / `("影片","电影")` / `("场次",)`。

**★ 这类最该修 —— 承诺了没做，比没承诺更误导。**

**接法**：加可选参数，默认值 = 原来写死的那套。
```
不传 ⇒ 行为与接线前完全一致（所有单测不用改）
传了 ⇒ 用配置的关键字
```
**保持纯函数**：不 import settings、不读盘（读配置是调用方的事）。

**★ 配置值【追加】在别名后面，不是替换**：
店主把关键字配成"影院"，但买家历史上会说"影城1""电影1" ——
替换掉别名就会把老买家的习惯用语弄坏。

**实测**：
```
默认：'影城2'→cinema, '电影3'→movie, '1'→(None,1)   ← 与接线前一致
配置：keyword_cinema="CINEMA" ⇒ 'CINEMA1'→cinema ✓  且别名仍生效
```
