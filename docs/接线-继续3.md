## 二、`no_ticket_reply` 为什么不能硬接

我把它想清楚了再动手，发现要接它得**新造一条路由**：

```
现在能向买家发话的路径只有【上游回调】——
   良票/万达回调 → 出票成功/失败 → 我们发对应的话。
而"买家索要票码但他没有出票成功的订单"这个场景，
   是【回调之外】的一种输入（买家主动问），系统从来没路由过。

⇒ 要接，必须：
   ① 在 on_message 里加一条"买家要票码"的路由
   ② 查一次账（本地订单库按 chat_id 找有没有 ticket_codes）
   ③ 有 → 发码；没有 → 发 no_ticket_reply
```

**①② 都是新逻辑，不是"读一下配置"。**

**★ 而且这里有个更根本的问题需要店主先定**：
```
"买家要票码"现在走的是【模型意图识别】（conversation_ai 的 HUMAN/其它意图）
+ read_order 工具。
⇒ 我再加一条确定性路由，会出现【两条路都能答同一个问题】——
  两条路的判据不一致时，就会出现"回了两遍"或"两边口径不同"。
```

**这正是我在关键词→知识库那次处理过的同一类问题**（`match()` 与 `search_faq`
两条路）。当时的结论是：**逐字可控的走代码，长尾走模型**。
所以这里要先定的是：
```
「买家要票码」算【逐字可控】还是【长尾】？
  · 逐字可控 ⇒ 加确定性路由，no_ticket_reply 就该接
  · 长尾     ⇒ 继续交给模型，这个设置项应该【从设置页拿掉】，不该留着当摆设
```

**⇒ 我没有替店主选。** 猜错的后果是"买家收到两遍不一样的回复"。

## 三、★ 一条我这轮才想清楚的界线

前面几轮我一直在"接 / 不接"之间反复。**现在这条界线清楚了**：

```
「接线」= 功能已经存在，只是没读配置。
          判据：能找到一段【已经在跑】的代码，把写死的值换成读配置。
          ⇒ 一小时内能做完，风险可验证。

「实现功能」= 要先想清触发时机、数据从哪来、异常路径怎么走。
          ⇒ 不是接线，是开发；而且必须先跟店主对齐语义。
```

**我这几轮一直在把"实现功能"误判成"接线"** ——
`auto_recognize` 那次对了（因为系统里有现成的"转人工"路径可复用），
`no_ticket_reply` / `offshelf_reply` / `ticket_image` 这次就错了
（没有现成路径，得新造）。

**★ 更好的判据**（比"能确定不该做什么"更准）：
```
能找到一个【已经在跑】的代码段，只把常量换成配置值  ⇒ 接线，可以做
需要新增一段控制流 / 新增一次数据查询 / 新增一条路由  ⇒ 实现功能，先对齐语义
```
