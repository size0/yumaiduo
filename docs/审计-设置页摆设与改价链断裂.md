## 二、★★★ 改价链是断的（比设置摆设严重）

店主定过「改价 = 选 C：先拍下、拍下后改价」。查这条链：

```
状态机：QUOTED + buyer.confirm → AWAIT_REPRICE → 发 bubble 17
        「已收到您的订单，您拍下不要付款，我改价后，您再付款~」  ✓ 发了
        AWAIT_REPRICE + order.repriced → AWAIT_PAY → 发 bubble 18（改价完成核对清单）
        SIDE_EFFECTS[order.repriced] = "REPRICE" → 落成 CHANGE_ORDER_PRICE 命令

插件端：CHANGE_ORDER_PRICE → executeReprice → client.orders.changePrice(...)  ✓ 完整
        （含 live 闸门、授权、读回验证、重试）

★★★ 但 Event.ORDER_REPRICED【没有任何生产者】：
     全仓搜 order.repriced / ORDER_REPRICED，只有
       · domain/conversation.py  —— 状态机表里的定义
       · tests/_demo_flow.py     —— 演示脚本手动推
       · tests/_smoke.py         —— 冒烟测试
     应用代码（application/）一处都没有。
```

### 后果（买家会真的卡住）

```
1. 买家拍下 → 收到「我改价后，您再付款」→ 等着
2. 但【从来没人调 orders.changePrice】⇒ 价格根本没改
3. bubble 18（改价完成核对清单）永远发不出去
4. 买家在那里干等一个不会发生的改价
```

### ★ 为什么插件端没有"改价成功"事件

查了插件端：**没有 `fish.reprice.success` 这类可订阅事件**。
改价是**下行命令**（我们发 → 插件调 changePrice → 回执行结果），不是上行事件。
插件把执行结果回投到 `/api/v1/commands/:id/result`。

**⇒ 正确的接法是：**
```
① 发完 CHANGE_ORDER_PRICE 后，等插件回投的执行结果
   （reprice.mjs 已经在结果里带 price_after_fen 与 order_status）
② 用那个结果推 ORDER_REPRICED（成功）或 ORDER_REPRICE_FAILED（失败）
③ 或者：不依赖改价结果，等 order.paid —— 买家既然付了款，
   说明他看到的价就是他要的价（此时 detail.payment 会告诉我们对不对）
```

**★ 这条要店主定走哪条**（关系到"改价失败怎么办"）：
```
路线 A：靠插件回投的改价执行结果 —— 准，但依赖插件把结果投回来
路线 B：不追改价结果，等 order.paid 时用 detail.payment 反查
        （我们已经有严格金额校验，付款金额不对会走 AMOUNT_MISMATCH）
路线 C：两条都接 —— 结果到了就提前推 AWAIT_PAY；没到就等付款
```
