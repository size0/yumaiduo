## 六、追加整改：你们查出的"第二处"（★★★）—— 5.1/5.2 无法用应用签名

**你们完全正确**，而且这条比文档问题严重：它是**实现缺陷**。

```
中间件：if path in {wplus-price, wplus-recovery}: 只认专用共享密钥 → 匹配后直接 call_next+return
        ↓ 应用签名分支根本走不到
路由层：_require_plugin_bridge_key(value) 又只比对专用共享密钥
⇒ 这两个接口【无法】使用应用签名
```

### 改法（已上线，`releases/unifyauth-bedeb4a`）

1. 新增 `backend/app/bridge_auth.py`：中间件验签成功后打标记
   （`request.state` + `ContextVar`，后者能被 anyio 派生的下游任务继承，
   所以不必给每个路由签名加参数）；
2. 中间件在 `call_next` **之前**打标记，并且**每个请求入口 `reset()`**，防止标记跨请求泄漏；
3. 路由层 4 处（5 个调用点）改为先看标记：
   `order.py` 的 5.1/5.2、`auth.py` 的号池依赖、`order_integration.py` 的
   `_require_bridge_key` 与 `_verify_worker_auth`。

### 线上实测（只带应用签名、**不带**任何桥密钥）

```
① 座位图        HTTP 200
② 号池          HTTP 200
③ 5.1 报价预览   HTTP 200   ← 修复前必是 401
④ 5.2 座位恢复   HTTP 200   ← 修复前必是 401
⑥ 遗留共享密钥行为不变：专用密钥→5.1 = 200；通用密钥→5.1 = 401；错误密钥→座位图 = 401
```

（⑤ 集成族只做了单测覆盖：线上环境变量里没配租户密钥，无法构造合法租户签名。
 单测 `test_app_signature_covers_all_bridges.py` 的 7 条覆盖了这条路径。）
