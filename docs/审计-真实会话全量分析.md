## 二、★★★ 断链的（我们问了，买家答了，我们听不懂）

### 2.1 数量 —— 最刺眼的一条

```
325 条买家在报数量，关键词只认 3 条。

  67×  1        49×  2张       47×  两张
  34×  一张      27×  1张       13×  2
  12×  3张       11×  是 2张     7×  3
```

**为什么这条最要紧：**
```
① 我们刚做的「张数待确认」提示，问的就是"要几个座位"
   ⇒ 买家真回答了，而系统【不认识】—— 我们问了他，他答了，我们听不懂
② ticket_count 直接决定金额（报价卡按 1 张算，实际 2 张 = 报错价）
③ 这里必须处理裸数字 `1` / `2` / `3` 与候选序号的歧义：
   现在 `1` 一律当候选序号（_parse_pick 返回 (None,1)），
   只有在"我们刚问过张数"时它才该被当张数
```

### 2.2 确认/同意 —— 775 条里 538 条接不住

```
接得住的（关键词 25 条里只有"好的"这一个）：
  108× 好的      16× 好的谢谢     9× 好的，谢谢    3× 好的！      3× 谢谢

★ 接不住的（全是同一件事的不同说法）：
   55× 好        44× OK          37× 可以        35× 对
   32× ok        29× 正确(逐字确认命中，见下)      24× 是的
   22× 是        14× 行          13× 收到        11× 嗯嗯
   10× okok       9× 好的，谢谢    8× 好嘞         8× 👌
    8× 嗯         7× 对的
```
**★ 「正确」29 次 —— 这个逐字确认是认的（`_is_confirm`），
但买家更常说「好」「可以」「OK」「对」，那些全都不认 ⇒ 单下不出去。**

### 2.3 问价格 —— 654 条里 644 条接不住

```
  54× 多少钱      18× 多少        13× 这个多少钱
  13× 什么价格     13× 什么价      7× 多少钱一张
   9× 改价吧       8× 改价
```
**模型有 `read_quote` 只读工具，能答 —— 但答得准不准要看它有没有拿到当前报价上下文。**

### 2.4 要求改价 —— 135 条，关键词只认 3 条

```
   9× 改价吧      8× 改价         4× 你改价
   4× 你改价吧     4× 改价格       3× 还能便宜吗
   2× 可以的，麻烦你改价，我拍下
```
**★ 这条不只是意图问题**：状态机里 `AWAIT_REPRICE` 只能靠
`buyer.confirm` / `buyer.ordered` 进（卖家侧改价流程），
"**买家主动要求改价**"这条路**根本没有事件可推**。
（`agent.py` 里写了 `request_reprice` 工具，触发词含「改价」，但没上线。）

## 六、我建议的动手顺序

```
第 1 步：数量意图（325 条，且是"我们自己问的自己听不懂"这种硬伤）
    · 新增意图 QUANTITY，只在"刚问过张数"时生效
    · 解决 `1` 的歧义：等候选序号时是序号，等张数时是张数
    · 定下 ticket_count → 重算价 → 出正确的报价卡

第 2 步：确认意图扩容（538 条，直接影响成单率）
    · 意图层已有 CONFIRM；实测 deepseek-flash 对
      「好的没问题」「可以，拍我吧」「要的」「OK」「嗯嗯行」都判对
    · 现在缺的是【让它有机会被调用】——它排在逐字确认和关键词之后，
      而「好」「OK」这些既不是逐字确认、也不是关键词 ⇒ 会走到它
    · ★ 但要注意：「你好」184 次不能判成 CONFIRM（状态机在 QUOTED 才放行，
      所以安全）—— 实测模型对「在吗」判 NONE、对「这个影院在哪」判 NONE，没误判

第 3 步：转人工（30 条，最安全的一条）
    · 「人工」「转人工」直接 need_human

第 4 步：文字实体抽取（526 条）
    · 照 agent.py 的 record_facts
    · 好处：买家不用截图也能起单

需要你先定的：
  · 第 6 项（买家要求改价）该走什么流程？
  · 第 4 项要不要现在做（它比意图层大）
```
