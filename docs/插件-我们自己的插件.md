# 我们自己的插件：验收与部署

> 日期：2026-10-14
> 位置：`yumaiduo/ticket-agent-plugin/`（V5 那个 `plugin-runtime/` 原样保留做回滚）

---

## 一、做了什么

从 V5 的插件壳改出**我们自己的插件**，核心是补上**自注册闭环**：

```
yumaiduo/ticket-agent-plugin/
├── yumaiduo.plugin.json     我们的 manifest（改名 + 端口对齐）
├── package.json             @xdl/ticket-agent-plugin
├── src/                     保留 V5 的 executor（发消息/改价/发货/取消）
│   ├── server.mjs           ★ 改了：自注册取 token + 热替换 + 交接 secret
│   └── register.mjs         注册调用
├── vendor/plugin-sdk-server 官方 SDK 0.20.0（从 0.19.0 升级）
└── test/acceptance.mjs      ★ 新写：13 条验收断言
```

### ★★★ 修的那个 bug（这是 `401 E_UNAUTHORIZED` 的根因）

```javascript
// 官方写法（im-auto-reply/index.mjs:531）
webhookSecret = data.webhookSecret ?? null;
pluginToken   = data.token ?? null;        // ★ 注册换回的新令牌

// V5 原来（server.mjs:27 + :25）
.then(data => { if (data.webhookSecret) cfg.secret = data.webhookSecret; })
//              ↑ data.token 被丢掉了
cfg.client = createPluginClient({
  pluginToken: process.env.YUMAIDUO_PLUGIN_TOKEN,   // ← 永远用 env 里那把
});
```

**⇒ 平台每次注册都发一把新令牌，而插件把它丢掉、一直用启动时 env 里那把。
⇒ 那把一旦被撤销，插件自己永远不会恢复。**

### 改了什么（4 处）

| # | 改动 | 为什么 |
|---|---|---|
| 1 | 注册响应取 `data.token`，用它重建 `cfg.client` | **根因**：不换就永远用旧令牌 |
| 2 | `YUMAIDUO_AUTO_REGISTER` 默认从 `false` 改成 `true` | 官方 §110：每次启动都要注册；关掉就只能靠静态令牌 ⇒ 必然失能 |
| 3 | 注册后把新 secret 写交接文件（0600） | 平台每次注册都换 secret；后端不知道就会验签全失败 |
| 4 | `/healthz` 暴露 `registration.tokenSource` | 出问题时能一眼看出用的是注册令牌还是 env 令牌 |

### manifest 改动（谨慎）

| 字段 | 改成 | 为什么 |
|---|---|---|
| `id` | **不动** `wanda-seat-autoquote` | 全局唯一+命名空间；改了＝新插件，webhook 路由断、租户要重订阅 |
| `vendor` | **不动** `xdl` | 必须等于入驻登记的 vendor，改了 403 |
| `entitlement.feature` | **不动** | 平台按它门控插件启用 |
| `name` | `电影票 AI 客服（ticket-agent）` | 这就是"我们的"（界面显示名） |
| `version` | `0.3.0 → 0.4.0` | |
| `runtime.port` | `4015 → 4100` | **声明值必须等于真实监听端口**（原来两者不一致） |

**权限没动**：10 项逐条核过，**每一项都有代码在用**（最小权限）。
订阅的 5 个事件也没动。

## 二、验收：13/13 通过（`node test/acceptance.mjs`）

测试用 **mock 平台 + mock 后端**，不依赖真实平台。判据的核心是第 3 组：

```
──── 1. 自注册 ────
[PASS] 插件启动后调用了 /api/v1/plugin/runtime/register
[PASS] /healthz 报告 registered=true
[PASS] 注册状态里能看出令牌来源是 register（不是 env）

──── 2. 接受注册返回的 webhookSecret ────
[PASS] 错误签名的 webhook 被拒（401）
[PASS] 用注册返回的 secret 签名 → 被接受（2xx）

──── 3. ★★★ 热替换：用注册返回的新令牌调平台 ────
[PASS] 平台收到了带【新令牌】的调用
[PASS] 平台【没有】收到带旧 env 令牌的调用（原 bug 就是这里）

──── 4. secret 交接文件 ────
[PASS] 交接文件已生成
[PASS] 文件里是注册返回的那个 secret
[PASS] 文件里记了令牌来源

──── 5. 事件转发到后端 ────
[PASS] 后端收到了 /api/v1/events
[PASS] 后端按新 secret 验签通过
[PASS] 事件内容被原样转发
```

**★ 为什么必须断言第 3 组**：只测"能启动""能收事件"的话，
**旧代码会全部通过** —— 而它正是坏的。必须断言"换回来的令牌被用上了"。
测试里我**故意给了一把过期 env 令牌**，这样才能验出"没有回退到旧令牌"。

## 三、★★★ 部署时必须做的一件事（否则静默必挂）

我查了后端 env，**现在有 `YUMAIDUO_WEBHOOK_SECRET`**。而 `plugin_secret()` 的优先级是：

```
① 环境变量 YUMAIDUO_WEBHOOK_SECRET      ← ★ env 在就会【挡住交接文件】
② 交接文件 V5_BACKEND_SECRET_FILE        ← 自注册换新 secret 走这条
③ 凭证文件兜底
```

**⇒ 如果 env 里留着旧的 secret，插件注册换新的之后，后端还在验旧的，
所有转发请求 401，而且看不出为什么。**（我实测确认了这个优先级。）

**所以部署时要**：
```bash
# 后端 env：去掉 YUMAIDUO_WEBHOOK_SECRET，加上交接文件路径
YUMAIDUO_WEBHOOK_SECRET=        ← 删掉这一行
V5_BACKEND_SECRET_FILE=/var/lib/ticket-agent/backend-secret.json   ← 加上
```

## 四、部署步骤（含回滚）

```bash
# ① 备份（V5 的插件目录不动，另有备份）
sudo cp /etc/ticket-system-v5/plugin.env /etc/ticket-system-v5/plugin.env.bak-before-own-plugin

# ② 上传我们的插件（另起目录，先不碰 V5 的）
rsync -av --exclude node_modules yumaiduo/ticket-agent-plugin/ \
      ubuntu@<host>:/home/ubuntu/ticket-agent-plugin/
# 装依赖（只有 json-bigint 一个）
cd ~/ticket-agent-plugin && npm install --omit=dev

# ③ 后端 env：去掉冲突的 secret，加交接文件
#    YUMAIDUO_WEBHOOK_SECRET=      ← 删
#    V5_BACKEND_SECRET_FILE=/var/lib/ticket-agent/backend-secret.json  ← 加
sudo mkdir -p /var/lib/ticket-agent && sudo chown ubuntu:ubuntu /var/lib/ticket-agent
sudo systemctl restart ticket-agent

# ④ 插件 env：
#    YUMAIDUO_AUTO_REGISTER=true    ← 打开自注册（★ 关键）
#    YUMAIDUO_PLUGIN_TOKEN=         ← 可以删了（注册会给新的）
#    V5_BACKEND_SECRET_FILE=/var/lib/ticket-agent/backend-secret.json
#    其它不动（PORT=4100 / CORE_URL / PLUGIN_DEVELOPER_TOKEN / BASE_URL / 各闸门）

# ⑤ 切换（同一个端口，同一个 pluginId ⇒ webhook 路由不变）
sudo systemctl stop ticket-system-v5-plugin
rsync -av ~/ticket-agent-plugin/ /opt/ticket-system-v5/plugin-runtime-new/
# 把 systemd 的 WorkingDirectory/ExecStart 指到新目录，或先手工起一次验证
sudo systemctl start <新服务>
```

### 回滚（1 分钟）
```bash
sudo cp /etc/ticket-system-v5/plugin.env.bak-before-own-plugin /etc/ticket-system-v5/plugin.env
sudo systemctl restart ticket-system-v5-plugin    # 指回 V5 目录
```
**★ V5 的插件目录原样保留**，回滚只是把指针换回去。

## 五、切换后要验的（按顺序）

```
1. /healthz → registered:true，且 registration.tokenSource == "register"
   ★ 如果是 "env"，说明平台没返回 token ⇒ 立刻回滚并查原因

2. 交接文件生成且内容非空
   ls -la /var/lib/ticket-agent/backend-secret.json      （应 600）
   ★ 且后端的 env 里【没有】YUMAIDUO_WEBHOOK_SECRET

3. 读店铺通了（这一步能直接验证新令牌有效）
   curl -s http://127.0.0.1:8801/api/shops
   ★ 期望 {"ok":true,"shops":[...]}；如果是 401/502 ⇒ 令牌或权限有问题

4. 让买家发一条消息 → /api/v1/events 有请求（这是我们至今还没验证过的一环）

5. 日志里不该再有 RECOVERY_INSPECTION_FAILED
```

## 六、这次学到的

```
① 「能启动 + 能收事件」通过 ≠ 插件是好的。
   旧代码在所有这些断言下都通过，而它调不动任何平台 API。
   ⇒ 断言必须打在【真正会坏的那一环】上（这里就是"令牌有没有被换掉"）。

② 配置优先级是静默杀手。
   env 挡住交接文件 ⇒ 新密钥读不到 ⇒ 全部验签失败，日志里只有 401。
   ⇒ 引入"文件交接"机制时，必须同时【清掉会遮蔽它的 env】。

③ 身份字段（id/vendor/feature）不是"名字"，是路由与授权。
   我一开始想改 id，查完才知道改了会让 webhook 路由断、租户要重订阅。
   ⇒ 改身份之前先问"谁在依赖它"。

④ 我上一轮的判断错了一半：
   我说"我们的插件就是 V5 的壳" —— 目录上确实是，
   但真正的问题是【那个壳缺了自注册闭环】，不是"壳不能用"。
   executor（发消息/改价/发货）本来就是插件该干的活，写得没问题，留下了。
```
